# OPT-20260808-003: 创建订单 1062 撞号修复复盘

**Status**: done
**Created**: 2026-08-08
**Related**: [[cross-subdomain-cookie-contract]]

## 背景

用户报障：www.daydaymoney.com `/tenant/*/billing/orders/create/` 创建订单失败，页面错误元素 `div.text-red-600` 显示「创建订单失败: Error 1062 (23000): Duplicate entry 'ORD-20260807-001' for key 'billing_resource_order.order_number'」，`data-traceid="5d680b8c-19c5-4959-9d06-8b68e47620ca"`。

## TraceId 日志时间线（Loki 本地 3100 命中）

- `task-auth` GET `/api/internal/gateway/forward-auth/` → **200**（鉴权通过）
- `task-bill` POST `/api/tenant/873472655125147648/billing/orders/` → **400**, `duration_ms: 3`（立即拒绝，无重试痕迹）
- 服务端**无错误明细日志**（仅 http_request 400），错误只存在于响应体 → 可观测性缺口

## 根因（三层叠加，任务 [taskBill/src/orders.go](taskBill/src/orders.go)）

1. **CAST 语法 MySQL 不兼容（主根因）**：`SELECT MAX(CAST(SUBSTR(order_number, 14) AS INTEGER)) ...` — `AS INTEGER` 在 MySQL 是非法语法（Error 1064），**每次执行必失败**。该 SQL 源于 SQLite 时代（SQLite 支持 INTEGER），MySQL 迁移（66fd85c「MySQL+SQLite dual-driver」）漏改。
2. **失败被静默吞掉**：`generateOrderNumber` 中 `if err == nil && maxSeq.Valid` — SELECT 报错时静默默认 `seq=1` → **同一 UTC 日内所有订单号都是 `xxx-001`** → 当日第一单成功后，之后每次创建都撞唯一键。
3. **重试检测文案不匹配**：`createOrder` 重试循环只识别 SQLite 文案 `"UNIQUE constraint failed"`，MySQL 的 `Error 1062 (23000): Duplicate entry ...` 永不命中 → 重试一次都不执行，直接 400。

## 修复（taskBill 00bbdb3）

- `AS INTEGER` → `AS SIGNED`（MySQL/SQLite 双兼容，实测验证）
- 新增 `isDuplicateKeyError`（兼容 MySQL `Duplicate entry` + SQLite `UNIQUE constraint failed`），重试两处检测替换
- SELECT 失败不再静默默认 seq=1，错误传播（Red 运行中该改动立即暴露了 1064 真根因）
- `maxRetries` 3 → 5（覆盖双击 + 客户端超时重试 + 管理端补建叠加并发）
- 新增 `resource_order_number_collision` / `resource_order_create_failed` 结构化日志（含 trace_id）→ Loki 可追踪

## 测试（orders_duplicate_test.go，Red→Green）

- `TestIsDuplicateKeyError`：MySQL/SQLite 文案单测
- `TestCreateOrderRetryOnDuplicateOrderNumber`：通过 `generateOrderNumberFn` 注入 seam 确定性模拟撞号 → 重试成功
- `TestCreateOrderConcurrentUniqueNumbers`：4 并发（50ms 延迟强制同时读 max）撞号收敛、序号唯一
- 修复前 3 例全 FAIL（并发测试失败文案与生产逐字一致），修复后全 PASS；taskBill 全量测试 24.9s 通过

## 经验

- **MySQL 迁移后必须验证每个 SQL 方言差异点**（CAST 类型名、LIMIT、反引号、ON DUPLICATE KEY），不能只依赖运行时不报错 — 本例 1064 被静默兜底后症状延迟数天才出现
- **静默兜底是根因放大器**：错误处理里「失败走默认值」的代码路径，一旦上游出错会把确定性故障伪装成偶发
- **错误明细必须带 trace_id 入日志**：本次只有 http_request 400 在 Loki，错误正文只在响应体，无日志无法区分「重试后成功」与「直接失败」
