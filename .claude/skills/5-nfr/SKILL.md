# /5-nfr — 非功能特性澄清

## 概述

在进入领域建模之前，对非功能需求（NFR）的支撑程度做出可验证的澄清。
NFR 的决策直接影响领域模型设计——

**价值流定义「做什么、按什么顺序做」，NFR 澄清定义「做到什么程度」，DDD 定义「怎么建模」。**

跳过此步骤的典型后果：过度设计（为不需要的规模建模）、设计不足（上线即瓶颈）、
领域模型返工（聚合边界因一致性需求调整）。

## 在流水线中的位置

```
1-brainstorming → 2-role-permission → [3-worktrees] → 4-value-stream → [5-nfr] → 6-ddd → 7-plans → 8-build → 9-review → 10-ship
                                                                          ↑
                                                                    你在这里
```

权威编号见 `.ai/11_ai_development/03_superpowers_workflow.md`。NFR 澄清在价值流之后、DDD 之前执行。价值流确定了增量范围和优先级；
NFR 澄清为每个增量标注质量要求；DDD 据此选择一致性模型、聚合粒度和架构模式。

## 何时使用

**触发条件：**
- 价值流已映射完毕，即将进入 DDD 建模
- 新功能涉及数据一致性、性能、安全或可用性决策
- 价值流增量中出现了需要权衡的场景（如：实时 vs 准实时、强一致 vs 最终一致）

**前置条件：** 已完成价值流映射（`/4-value-stream`），有明确的价值增量文档。

**跳过条件：**
- 纯 UI 样式调整、文档修改、配置变更
- 增量不引入新的数据流或外部依赖
- 设计文档中已明确声明「无特殊 NFR 要求」

**注意：即使跳过，仍需在输出中声明跳过的理由。**

## 执行清单

你必须为以下每一项创建任务并按顺序完成：

1. **读取价值流与设计文档** — 了解增量范围和已有设计约束
2. **路径分片键强制审视（硬门禁）** — 枚举增量中全部 API/前端路由/消息路由键等路径；无分片 ID → 评估可伸缩性需求；有分片 ID → 评估是否合适。细则见 [references/path-shard-id-scalability.md](./references/path-shard-id-scalability.md)；元规则 `.ai/01_project_constraints/48_nfr_path_shard_id_scalability.md`
3. **幂等性强制审视（硬门禁）** — 枚举全部副作用路径（HTTP 写、事件消费、Webhook、timer、出站写调用）；写明重复触发源、业务重复边界、幂等键与重放语义；键须与边界同粒度。细则见 [references/idempotency.md](./references/idempotency.md)；元规则 `.ai/01_project_constraints/53_nfr_idempotency.md`
4. **筛选适用 NFR 类别** — 从 NFR 分类体系中选出相关的维度（路径审视结论会强制把「可伸缩性」纳入相关类别，除非全部路径已书面证明 L0；幂等性审视会强制把「数据一致性」和/或「容错机制」纳入，除非全部路径已书面证明无副作用 L0）
5. **逐类别定义支撑程度** — 使用 5 级尺度为每个类别定性
6. **编写质量场景** — 用「刺激-响应」模板把 NFR 变成可验证的场景
7. **标注领域模型影响** — 每个 NFR 决策如何影响 DDD 建模
8. **记录权衡与边界** — 明确不做什么以及跨 NFR 的取舍
9. **写入 NFR 澄清文档** — 输出到 `docs/superpowers/plans/`（须含「路径分片键审视」表与「幂等性审视」表）
10. **自检** — 每个场景可验证、每个决策有边界、路径分片键审视与幂等性审视完整

## NFR 澄清流程

### 1. 读取价值流与设计文档

加载：
- 设计文档：`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
- 价值流文档：`docs/superpowers/plans/YYYY-MM-DD-<topic>-value-stream.md`

按价值流增量逐一切片，只澄清当前增量的 NFR。不为未来增量预判。

### 2. 路径分片键强制审视（硬门禁）

在筛选 NFR 类别**之前**，必须枚举当前增量涉及的全部路径，并按下列分支处理（完整决策树与适配性清单见 [references/path-shard-id-scalability.md](./references/path-shard-id-scalability.md)）：

| 路径情况 | 必须做的事 |
|----------|-----------|
| **未携带可分片 ID**（如无 `tenantId`/`companyId` 等） | **必须**评估是否存在可伸缩性需求（L0–L4）。有需求则给出补键/强制 query/全局索引上限等动作；标 L0 须写理由 + 升级触发条件 |
| **已携带分片 ID** | **必须**评估该 ID 是否为**合适**的分片键（基数、访问对齐、租户隔离、稳定性、热点、与库表分片策略一致）。不合适则记录正确分片键与路径/事件键纠正动作 |

**禁止**：因「可伸缩性看起来无关」而跳过本步；跳过须在 Hard Gate 失败。路径审视结果写入 NFR 文档的「路径分片键审视」表，并驱动下方「可伸缩性」类别是否进入第 5 步及定级。

### 3. 幂等性强制审视（硬门禁）

在筛选 NFR 类别**之前**（可与 §2 并行），必须枚举当前增量的副作用路径，并按下列分支处理（完整决策树与键适配性清单见 [references/idempotency.md](./references/idempotency.md)）：

| 路径情况 | 必须做的事 |
|----------|-----------|
| **无副作用**（纯 GET/查询） | 可标幂等性 L0，**须写理由**。禁止把发事件、写审计、出站写等隐式副作用标成只读 |
| **有副作用** | **必须**写明：重复触发源、业务重复边界、幂等键、重放语义、键持久化。判定键是否与边界**同粒度**。过粗或过细则记录纠正动作。若触发源含用户点击/双击，须同时规划前端按钮防重放（元规则 52 / `.ai/01_project_constraints/57_frontend_button_anti_replay.md`） |

**禁止**：因「看起来会自然幂等」或「消费者会去重」而跳过本步；**禁止**默认用 `company_id` / `tenant_id` / `user_id` 作事件消费幂等键。资金/配额/云资源/支付路径默认 ≥ L3。结果写入 NFR 文档的「幂等性审视」表，并驱动「数据一致性」「容错机制」是否进入第 5 步。

### 4. 筛选适用 NFR 类别

从以下分类中筛选与当前增量**实际相关**的维度。无关的类别标注「不适用」并省略后续分析。

#### NFR 分类体系（基于 ISO 25010 精简）

**性能 (Performance)**
- 响应时间（P50 / P95 / P99 / P999）
- 吞吐量（每秒请求数 / 每秒事务数）
- 并发用户数 / 并发连接数
- 批处理耗时窗口
- 长尾延迟放大 (tail latency amplification)：一个用户请求在服务端可能触及多个下游，端到端 P99 ≠ 各下游 P99 之和，少量慢请求会放大整体延迟分布
- 排队模型：请求在队列中的等待时间 vs 处理时间，高负载下排队延迟主导 P99
- **读路径缓存（可选）**：读路径性能 ≥ L2、或多实例共享易失状态时，引用 [references/redis-cache.md](./references/redis-cache.md) 判定是否缓存、键/TTL/失效/未命中/Redis 宕机语义；**不是硬门禁**

**可伸缩性 (Scalability)**
- 水平扩展 vs 垂直扩展策略
- 数据量级预期（日增行数、总行数、存储量）
- 峰值流量倍数（相对日均）
- 分区策略：按键分区 (key-based / hash) vs 范围分区 (range) vs 二级索引分区，选型影响聚合 ID 设计和跨分区查询模式
- 再平衡机制：固定分区数 / 动态分区 / 一致性哈希，决定扩容时数据迁移的代价和窗口
- **路径分片键（强制）**：无分片 ID 的路径是否仍需伸缩；有分片 ID 时该键是否合适（见 §2 与 [path-shard-id-scalability.md](./references/path-shard-id-scalability.md)）

**可用性 (Availability)**
- 正常运行时间目标（99.9% → 99.99% → 99.999%）
- 故障恢复时间目标 (RTO)
- 数据丢失容忍度 (RPO)
- 降级策略（哪些功能可在故障时关闭）

**安全性 (Security)**
- 认证强度（单因子 / 双因子 / 无密码）
- 授权粒度（RBAC / ABAC / ReBAC）
- 数据加密（传输中 / 静态 / 端到端）
- 审计追踪要求
- 多租户数据隔离级别

**数据一致性 (Consistency)**
- 事务隔离级别：Read Committed / Snapshot Isolation / Serializable —— 决定并发读写时能看到什么
- 分布式一致性梯度：线性一致 → 顺序一致 → 因果一致 → 最终一致 → 读己之写 / 单调读 / 一致前缀读（这些是最终一致的实用中间态，应显式选用而非笼统说「最终一致」）
- 跨服务事务边界（Saga / 两阶段提交 / 补偿事务 / Outbox Pattern）
- **幂等性（强制）**：幂等键策略（客户端生成 / 业务键去重 / 数据库唯一约束），exactly-once 语义的实现边界（at-least-once + 幂等消费 = effectively-once）。键必须与业务重复边界同粒度（见 §3 与 [idempotency.md](./references/idempotency.md)）
- 乱序容忍与去重窗口

**容错机制 (Fault Tolerance)**
- 超时策略：连接超时 vs 请求超时，超时传递 (timeout propagation)，级联超时放大风险
- 重试策略：指数退避 (exponential backoff) + 抖动 (jitter)，最大重试次数，重试放大效应 (retry amplification)
- 断路器 (Circuit Breaker)：熔断阈值、半开探测、恢复策略
- 舱壁隔离 (Bulkhead)：线程池/连接池隔离，防止一个下游故障耗尽所有资源
- **幂等消费保障（强制）**：at-least-once + 幂等键 → effectively-once；禁止用租户/用户级粗字段当默认消费键（见 §3）

**可观测性 (Observability)**
- 日志级别和保留期
- 指标采集粒度（业务指标 / 技术指标）
- 链路追踪覆盖率
- 告警响应时间要求

**合规与隐私 (Compliance)**
- 数据本地化（是否允许跨境）
- 数据保留/删除策略 (GDPR 遗忘权)
- 行业标准（SOC2 / HIPAA / PCI-DSS）

**可维护性 (Maintainability)**
- 部署频率和回滚窗口
- 向后兼容承诺（覆盖范围：API / 数据模型 / SDK / 配置文件格式）
- API 版本策略（语义化版本、废弃字段保留周期）
- 特性开关 / 灰度发布需求

**只有与该增量确实相关的类别才进入第 5 步。** 多数增量只涉及 2-4 个类别。
例外：
- 完成 §2 路径审视后，凡存在「无分片 ID 且未书面证明可伸缩性 L0」或「分片 ID 不适配」的路径，**可伸缩性类别不得标为跳过**。
- 完成 §3 幂等性审视后，凡存在「副作用路径且未书面证明幂等性 L0」或「幂等键不适配」的路径，**数据一致性与容错机制不得同时标为跳过**（至少保留与幂等相关的那一类并定级）。

### 5. 逐类别定义支撑程度

为每个相关类别选择一个支撑等级。等级必须具体——禁止使用「好用」「稳定」等模糊词。

#### 5 级支撑尺度

| 等级 | 名称 | 含义 | 触发信号 |
|------|------|------|---------|
| L0 | **不需要** | 此 NFR 在当前增量中无要求 | 该类别与核心功能无关 |
| L1 | **基础** | 满足最低可运行标准，不做专项投入 | 内部工具、原型、低频操作 |
| L2 | **标准** | 满足通用业务预期，有量化目标 | 多数 B2B SaaS 功能 |
| L3 | **增强** | 超出标准，有专项设计和测试 | 付费功能、差异化竞争点 |
| L4 | **极致** | 行业领先水平，需要架构级投入 | 核心卖点、合规刚需、安全命脉 |

**判断辅助：**

```
问：把这个做到 L4 是否值得多花 3 倍的研发成本？
      ↓ 否                    ↓ 是
降一级考虑              问：做不到这个等级是否会丢失客户或违反法规？
                              ↓ 否              ↓ 是
                        保持当前评估          这就是你的底线等级
```

**示例：**

```
NFR 类别: 性能
适用增量: Increment 1 (任务创建 API)
支撑等级: L2 - 标准
量化目标: P50 < 200ms, P95 < 500ms, P99 < 2s（均为服务端处理时间，不含网络延迟）
场景描述: 用户在 Web 端创建任务，点击保存后 200ms 内得到确认
```

### 6. 编写质量场景 (Quality Attribute Scenarios)

每个相关 NFR 类别至少写一个**可验证**的质量场景。使用「刺激-响应」六要素模板：

#### 场景模板

```
场景 ID: QS-{序号}
类别: {NFR 类别}
等级: L{0-4}
场景描述: {一句话描述}

刺激源: {谁/什么触发？例如：用户点击、定时任务触发、依赖服务宕机}
刺激: {具体事件是什么？例如：100 个并发用户同时提交表单}
制品: {系统哪部分被刺激？例如：任务创建 API}
环境: {正常/峰值/降级/故障恢复}
响应: {系统应该如何反应？量化为可观察的指标}
响应度量: {如何验证响应是否达标？给出具体数字和测量方式}
```

#### 完整示例

```
场景 ID: QS-01
类别: 性能
等级: L2
场景描述: 用户在正常负载下创建任务，200ms 内得到确认

刺激源: Web 客户端用户
刺激: 提交任务创建表单（包含标题和描述）
制品: 任务创建 API (POST /api/tasks)
环境: 正常负载（日均 2× 的并发量）
响应: 返回 201 Created，包含任务 ID 和创建时间
响应度量: 服务端处理时间 P95 ≤ 500ms，由 APM 工具在服务端测量（不含网络）
```

```
场景 ID: QS-02
类别: 数据一致性
等级: L3
场景描述: 用户删除工作空间时，关联任务的归属处理

刺激源: 工作空间所有者
刺激: 发起删除工作空间请求
制品: 工作空间服务 + 任务服务
环境: 正常
响应: 工作空间标记为删除，关联任务异步转移至「未分类」，30 秒内完成
响应度量: 任务转移最终一致，幂等——重复删除请求不产生副作用
```

```
场景 ID: QS-03  类别: 一致性/容错  等级: L2
刺激: 相同 Idempotency-Key / event_id 连续两次提交（超时重试或 Kafka 重投）
响应度量: 副作用恰好 1 次；第二次返回首次结果或空操作成功
```

**场景即测试契约。** 增量含副作用路径且幂等性 ≥ L2 时，至少包含一个「重复提交/重投」QS。

### 7. 标注领域模型影响

NFR 决策直接改变 DDD 建模方向。对每个影响 DDD 的 NFR 决策做标注：

| NFR 决策 | 领域模型影响 | 具体动作 |
|----------|-------------|---------|
| 线性一致 / Serializable (L3-L4) | 聚合不能拆分，相关实体必须在同一聚合边界内 | DDD 步骤采用大聚合设计 |
| 因果一致 / 最终一致 (L1-L2) | 不同实体可分布在不同的限界上下文，通过事件通信 | DDD 步骤采用小聚合 + 领域事件，事件携带因果依赖 (vector clock / logical timestamp) |
| 读己之写 / 单调读 (L2) | 读模型需要版本追踪，用户读取自己的写入必须路由到主节点 | 仓储接口增加主库读方法，查询端增加 session affinity |
| 可用性 ≥ L3 | 关键聚合需要降级策略接口，缓存兜底 | 仓储接口增加 `find_with_fallback()` 方法 |
| 分区策略为 key-hash (L2+) | 聚合 ID 必须天然适配分区键，避免跨分区查询 | 聚合根 ID 使用分区友好的键（如 tenant_id 前缀） |
| **路径无分片 ID 且可伸缩性 ≥ L1** | 聚合/API/事件缺少扩容边界 | 契约与聚合根补分片键；仓储禁止无键扫描 |
| **路径分片 ID 不适配** | 错误身份成为分区边界 | 改聚合身份与仓储必参为正确分片键；对齐路径/Topic key |
| 断路器 + 超时 (L2+) | 领域服务调用外部时必须通过防腐层，不可直连 | 领域服务接口保持纯业务，resilience 逻辑在基础设施层实现 |
| 幂等消费 (L2+) | 实体操作必须是幂等的——状态转移而非增量变更 | 实体方法用 `activate()` / `mark_as(status)` 而非 `increment()` |
| **副作用路径缺幂等键或键过粗** | 重复投递会双写，或过粗键吞掉后续合法意图 | 命令/事件契约补与业务重复边界同粒度的键；禁止默认 `company_id`/`user_id` |
| **幂等键不适配** | 错误身份成为去重边界 | 改事件/命令身份与仓储去重必参；对齐 HTTP Idempotency-Key 与消费者键 |
| 多租户隔离 ≥ L3 | 租户 ID 必须出现在所有聚合根上 | 实体基类增加 `tenant_id` 字段 |
| 审计追踪 ≥ L2 | 关键操作需建模为领域事件 | 新增 AuditEvent 领域事件类型 |
| 性能 ≥ L3 / 长尾延迟控制 | CQRS 分离读写模型；读路径可接受最终一致 | DDD 步骤同时建模读模型和写模型 |
| 安全性 L4 | 领域服务需要授权检查点 | 领域服务接口增加 `actor` 参数 |
| 事务隔离级别 ≥ Snapshot Isolation | 聚合内状态变更不可基于过期快照 | 实体增加 `version` 字段用于乐观锁 |

只标注真正影响模型的决策。L0-L1 的 NFR 通常不影响领域模型（路径分片键审视与幂等性审视结论除外：即使可伸缩性/幂等性 L1 也须写入模型影响）。

### 8. 记录权衡与边界

明确声明：

**做了什么取舍：**
```
- 选择最终一致性（L2 一致性）以换取任务创建的低延迟（L3 性能）
- 工作空间删除采用异步而非同步，接受 30 秒的最终一致窗口
```

**明确不做什么：**
```
- 不在 V1 实现实时协作编辑（L4 一致性），单用户编辑为主
- 不支持跨境部署（L0 数据本地化），仅国内部署
- 不做 P99 < 100ms 的极致性能优化（保持 L2 标准），功能完整性优先
```

**边界条件——触发升级：**
```
- 当日活用户超过 10 万时，性能从 L2 升级到 L3 —— 届时需要 CQRS 拆分
- 当客户要求 SOC2 合规时，审计从 L1 升级到 L3 —— 需要全量操作日志
```

### DDD 步骤如何使用本步骤的输出

DDD 步骤在执行时必须引用 NFR 澄清文档中的决策：

- **聚合大小**：强一致性要求 → 大聚合；最终一致性 → 小聚合 + 事件
- **仓储接口**：可用性要求 → 补充降级/兜底方法；**路径分片键审视**要求仓储查询必带合适分片键
- **领域事件**：审计要求 → 补充审计事件类型；事件路由键与路径分片键对齐
- **领域服务签名**：安全要求 → 注入 `actor` 参数
- **是否使用 CQRS**：性能要求 → 读写模型分离
- **分片边界**：无分片 ID 且需伸缩 → 补聚合根/契约分片键；分片 ID 不适配 → 纠正聚合身份与路径
- **幂等边界**：**幂等性审视**要求命令/事件携带与业务重复边界同粒度的键；仓储按该键去重；实体用状态转移而非增量累加

> "NFR 文档要求最终一致性（L2），因此本限界上下文采用小聚合 + 领域事件解耦方案。"
> "路径分片键审视判定 tenantId 合适（L2 可伸缩性），因此仓储所有查询以 tenant_id 为必参。"
> "幂等性审视判定 TASK_CREATED 消费键为 task_id（L2），禁止用 user_id；重复投递不产生第二次 fanout。"

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 所有 NFR 都标 L3/L4 | 按实际需要定级，过度设计和设计不足同样有害 |
| 质量场景缺少数字 | 「响应要快」→ 改为「P95 ≤ 500ms」 |
| NFR 决策与 DDD 模型无关联 | 每个影响模型的 NFR 决策标注具体 DDD 动作 |
| 只说做什么、不说边界 | 「不做什么」和「升级触发条件」同等重要 |
| 跳过 NFR 澄清不声明理由 | 跳过的类别注明「不适用 + 原因」 |
| 混淆日均与峰值 | 性能目标要区分正常负载和峰值负载的环境参数 |
| 路径无分片 ID 却跳过可伸缩性 | 必须评估伸缩需求；L0 须写理由 + 升级触发 |
| 路径有 ID 即当作合适分片键 | 用适配性清单判定；如仅 `memberId` 常不足以作租户分片键 |
| 「以后再加 tenantId」拖延 | 在 NFR 文档写明动作；DDD/计划须消化，不得无记录进入实现 |
| 写路径不谈幂等、或写「自然幂等」无键 | 必须填「幂等性审视」表；副作用路径写清键与重放语义 |
| 用 `company_id`/`user_id` 当默认消费键 | 键必须与单次业务意图同粒度（`event_id`/`task_id`/业务单号） |
| 每次重试新生成 UUID 当作幂等键 | 客户端须在重试时回传同一键；否则防不住超时重放 |
