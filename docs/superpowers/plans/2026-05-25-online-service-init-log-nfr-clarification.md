## NFR 概览表

| 类别 | 等级 | 一句话量化 |
|------|------|-----------|
| 可观测性 | L3 | 每次启动在 `logs/init.log` 追加 1 条结构化快照，覆盖启动关键环境变量 |
| 可用性 | L2 | `init.log` 写入失败不阻断服务启动，主服务可继续监听并提供 API |
| 性能 | L1 | 启动期额外日志写入开销控制在单次 20ms 量级内（本地磁盘场景） |
| 安全性 | L1（调试例外） | 按需求记录原始环境变量值，不做脱敏；仅限本地状态目录访问 |
| 可维护性 | L2 | 日志格式固定为 JSON Lines，字段语义稳定，便于后续工具解析 |

## 逐增量 NFR 分析

### Increment 1: init.log 启动快照薄切片

#### NFR 类别: 可观测性
- **等级**: L3 - 增强
- **量化目标**:
  - 每次 `onlineServiceJS` 进程启动，`logs/init.log` 新增 1 行 JSON 记录
  - 记录中必须包含 `ts/event/pid/port/env` 字段
  - 当 `DEBUG_AGENT` 在启动环境中存在时，`env.DEBUG_AGENT` 值可追溯
- **质量场景**: QS-01

#### NFR 类别: 可用性
- **等级**: L2 - 标准
- **量化目标**:
  - 即使 `init.log` 写入异常（目录权限/磁盘错误），服务仍完成 `listen`
  - 启动 API 可达性不受影响（`/health` 正常返回）
- **质量场景**: QS-02

#### NFR 类别: 性能
- **等级**: L1 - 基础
- **量化目标**:
  - 启动阶段新增日志写入操作不引入可感知的启动退化（目标：单次写入 20ms 量级）
  - 不引入循环写盘，不在请求热路径执行

#### NFR 类别: 安全性
- **等级**: L1 - 基础（调试例外）
- **量化目标**:
  - 按当前需求，`init.log` 保留原值，不做脱敏/截断
  - 仅写入 `ONLINE_PROJECT_STATE_ROOT/logs/`，不新增对外暴露接口

### Increment 2: 可选白名单采集（`INIT_LOG_ENV_KEYS`）

#### NFR 类别: 可维护性
- **等级**: L2 - 标准
- **量化目标**:
  - 当配置 `INIT_LOG_ENV_KEYS` 时，仅记录白名单键，输出字段可预测
  - 未配置时保持向后兼容（全量采集）
- **质量场景**: QS-03

## 质量场景

### QS-01: 启动快照完整可追溯
| 要素 | 内容 |
|------|------|
| 类别 | 可观测性 |
| 等级 | L3 |
| 刺激源 | relayToTrae 启动 onlineServiceJS |
| 刺激 | 触发一次新进程启动 |
| 制品 | `onlineServiceJS` 启动流程（`main()` 前段） |
| 环境 | 正常本地开发运行 |
| 响应 | 在 `logs/init.log` 追加一条 JSON 快照，包含启动环境 |
| 响应度量 | 启动后读取 `init.log` 末行，断言存在 `event=onlineServiceJS.init` 且 `env.DEBUG_AGENT` 可见（若传入） |

### QS-02: 写入失败不阻断启动
| 要素 | 内容 |
|------|------|
| 类别 | 可用性 |
| 等级 | L2 |
| 刺激源 | 文件系统异常（权限不足/写失败） |
| 刺激 | 启动阶段尝试写 `init.log` 失败 |
| 制品 | `onlineServiceJS` 启动流程 |
| 环境 | 故障注入（mock fs append 抛错） |
| 响应 | 记录错误（stderr 或内部告警）并继续服务启动 |
| 响应度量 | 进程仍完成 `listen`，`/health` 返回 200；不存在因 init 日志失败导致的 `process.exit` |

### QS-03: 白名单采集行为稳定
| 要素 | 内容 |
|------|------|
| 类别 | 可维护性 |
| 等级 | L2 |
| 刺激源 | 运维配置 `INIT_LOG_ENV_KEYS` |
| 刺激 | 启动服务并写入 `init.log` |
| 制品 | 环境变量采集模块 |
| 环境 | 正常运行（配置了白名单） |
| 响应 | 日志只包含白名单键，且键集合稳定 |
| 响应度量 | 单测断言 `env` 对象键集合与白名单完全一致；未配置时仍为默认全量采集 |

## 领域模型影响

| NFR 决策 | 模型影响 | 对应 DDD 动作 |
|----------|---------|-------------|
| 可观测性 L3（启动快照必须可追溯） | 需要明确“启动快照”领域对象边界 | 在 DDD 中保留 `OnlineServiceInitSnapshot` 作为独立实体/值对象 |
| 可用性 L2（写失败不阻断） | 启动日志从主启动事务中解耦 | 在领域服务中将日志写入定义为 best-effort，不参与成功判定 |
| 可维护性 L2（结构化稳定输出） | 需要固定契约字段 | 在 DDD 中为 `env` 采集规则建模（默认全量 + 可选白名单策略） |
| 安全性 L1 调试例外（原值落盘） | 安全边界靠运行环境而非领域规则 | 在 DDD 中显式记录“当前版本不脱敏”为策略约束，避免隐式行为漂移 |

## 权衡与边界

### 取舍
- 选择“可观测性优先”：允许记录完整 env 原值，以快速定位 relay/env 透传问题。
- 选择“可用性优先”：日志写入失败不影响服务启动，避免次要能力反向阻塞主链路。

### 明确不做什么
- 本增量不引入数据库持久化，不构建日志检索 API。
- 本增量不做日志脱敏策略引擎（遵循当前调试需求）。
- 本增量不做日志轮转系统改造（沿用现有文件追加模式）。

### 升级触发条件
- 若出现敏感信息合规要求（例如审计或外部监管），安全级别从 L1 升级到 L3，需引入脱敏/密文策略。
- 若 `init.log` 体积增长显著影响排障效率，维护性从 L2 升级到 L3，需引入分级采集和轮转策略。

## 跳过声明

- **可伸缩性**: 跳过。该功能仅在启动阶段单次写入，对吞吐与水平扩展无直接要求。
- **数据一致性**: 跳过。无跨服务状态写入与事务边界，不涉及强一致/最终一致取舍。
- **合规与隐私**: 跳过（当前版本）。已有明确调试例外策略，后续按升级触发条件处理。
