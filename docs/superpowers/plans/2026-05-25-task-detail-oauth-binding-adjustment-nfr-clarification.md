## NFR 概览表

| 类别 | 等级 | 一句话量化 |
|------|------|-----------|
| 性能 | L2 | 预检接口服务端 P95 ≤ 800ms，仓库行级 OAuth 状态检查单次请求 P95 ≤ 500ms（不含网络） |
| 安全性 | L2 | 仅允许同 task scope 的 token 访问，错误响应不泄露敏感 token |
| 数据一致性 | L2 | 仓库授权保存后 5 秒内可被启动预检读取（读己之写），并按 `repo_url` 判定绑定可见性 |
| 可观测性 | L2 | 预检失败 100% 返回 `error_code + trace_id + missing_repo_credentials` |
| 可维护性 | L2 | 维持现有 API 契约向后兼容，变更必须有单测与 e2e 回归 |
| 可用性 | L1 | 不增加专门高可用机制，沿用现有服务可用性基线 |

## 逐增量 NFR 分析

### Increment 1: 仓库行级 OAuth 入口薄切片

#### NFR 类别: 可维护性
- **等级**: L2 - 标准
- **量化目标**:
  - 不新增后端 API，仅扩展已有连接状态查询参数（`repo_url`）
  - 前端单测覆盖“同页多仓库仅未绑定行显示 OAuth 按钮”
- **约束**: 保持已有 `app/start` 与 `github-credential-approve` 行为不变，移除全局按钮改为行级动作

#### NFR 类别: 安全性
- **等级**: L2 - 标准
- **量化目标**: OAuth 流程不降低原有 token 边界，前端不展示 access/refresh token 明文
- **约束**: `repo_url` 仅用于 provider/域名判定，不作为授权绕过入口

### Increment 2: 启动前预检可视化引导

#### NFR 类别: 性能
- **等级**: L2 - 标准
- **量化目标**:
  - `repo-credentials-precheck` 服务端处理时间 P50 ≤ 300ms，P95 ≤ 800ms
  - 失败提示在单次启动动作内返回（前端 3 秒内可见）
- **约束**: 不增加额外远程链路，仅复用既有预检调用

#### NFR 类别: 数据一致性
- **等级**: L2 - 标准
- **量化目标**:
  - 用户完成仓库授权保存后，5 秒内预检可读取到最新绑定结果
  - 预检失败时 `missing_repo_credentials` 与后端覆盖率计算一致
- **约束**: 当前接受短暂最终一致窗口，不要求跨服务强一致事务

#### NFR 类别: 可观测性
- **等级**: L2 - 标准
- **量化目标**: 预检失败响应 100% 包含 `error_code`、`trace_id`、`missing_repo_credentials`
- **约束**: 前端日志与 UI 提示透传 `trace_id` 语义（不要求页面显式展示 trace_id）

### Increment 3: 契约稳定性回归保护

#### NFR 类别: 可维护性
- **等级**: L2 - 标准
- **量化目标**:
  - 后端契约测试覆盖 409 场景关键字段
  - 前端单测覆盖 OAuth 文案与仓库绑定保存路径
  - e2e 覆盖“预检失败阻断 start + 显示引导”
- **约束**: 回归测试必须在本地可执行，避免仅文档化不落地

#### NFR 类别: 可用性
- **等级**: L1 - 基础
- **量化目标**: 失败可重试，不新增容灾/降级分支
- **约束**: 依赖现有服务稳定性，不在本增量引入 HA 架构投入

## 质量场景

### QS-01: 预检性能基线
| 要素 | 内容 |
|------|------|
| 类别 | 性能 |
| 等级 | L2 |
| 刺激源 | 任务详情页用户 |
| 刺激 | 点击“启动”，触发 `repo-credentials-precheck` |
| 制品 | `POST /relay-to-trae/repo-credentials-precheck/` |
| 环境 | 正常负载（工作日常规并发） |
| 响应 | 返回预检通过或结构化失败 |
| 响应度量 | 服务端处理时间 P95 ≤ 800ms（APM 统计，不含网络） |

### QS-02: 授权保存后的读己之写
| 要素 | 内容 |
|------|------|
| 类别 | 数据一致性 |
| 等级 | L2 |
| 刺激源 | 同一用户 |
| 刺激 | 完成仓库“保存账号”后立即点击“启动” |
| 制品 | `github-credential-approve` + `repo-credentials-precheck` |

| 响应 | 最多一次短暂失败后可成功通过预检 |
| 响应度量 | 5 秒内预检结果反映最新绑定；`missing_repo_credentials` 不再包含已保存仓库 |

## 领域模型影响

| NFR 决策 | 模型影响 | 对应 DDD 动作 |
|----------|---------|-------------|
| 数据一致性 L2（读己之写，允许短暂最终一致） | 不要求跨上下文强一致大聚合；需要稳定的仓库地址到绑定状态映射 | 保持小聚合；通过领域服务编排“绑定保存→预检读取”链路，并在仓储边界显式保留 `repo_url -> repo_slug` 映射 |
| 安全性 L2（task scope 强约束） | 领域服务需感知操作者与任务作用域 | 在相关领域服务接口中显式传入 `actor/task_scope` 并校验 |
| 可观测性 L2（结构化失败契约） | 失败状态需可追踪，不可只返回字符串 | 将失败分类抽象为值对象（错误码 + 缺失集合 + trace_id） |
| 可维护性 L2（API 向后兼容） | 避免扩散临时字段/隐式约定 | 在应用层维持稳定契约，新增字段走显式版本化或兼容扩展 |

## 权衡与边界

### 取舍
- 选择 L2 一致性（读己之写 + 短暂最终一致）而非 L3 强一致，换取实现复杂度可控与交付速度。
- 选择 L2 性能基线（P95 ≤ 800ms）而非极致低延迟，优先保证“可诊断、可操作”的失败体验。

### 明确不做什么
- 不在 V1 引入失败原因细分类字段（`no_identity` 等），先用缺失仓库列表完成可操作闭环。
- 不在本增量引入新的高可用与灾备机制（如多活、自动故障转移）。
- 不重构 OAuth 发证链路与 token 生命周期策略。
- 不在本增量实现跨页面统一 OAuth 状态总线（仅保证 task-detail 仓库行级行为正确）。

### 升级触发条件
- 当预检 P95 连续一周 > 800ms：性能从 L2 升级到 L3，评估缓存/CQRS 或链路拆分。
- 当企业客户要求审计闭环：可观测性从 L2 升级到 L3，补充可检索审计事件流水。
- 当出现跨 provider 大规模授权失败：一致性与安全从 L2 升级，补充失败原因分类与补偿流程。

## 跳过声明

- 可伸缩性: 跳过。当前增量为交互与契约增强，不引入新高流量入口。
- 合规与隐私: 跳过。无新增个人敏感数据字段与跨境数据处理。
- 容错机制: 跳过。当前仅复用既有重试与超时策略，本增量不新增外部调用链路。
