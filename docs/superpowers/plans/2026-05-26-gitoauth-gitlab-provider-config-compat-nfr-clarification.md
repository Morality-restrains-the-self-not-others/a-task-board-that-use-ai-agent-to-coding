## NFR 概览表

| 类别 | 等级 | 一句话量化 |
|------|------|-----------|
| 性能 | L2 | OAuth start 到 302 重定向的服务端 P95 <= 300ms（不含外部 GitLab 页面加载） |
| 一致性 | L2 | 相同 `repo_url + service_provider` 在同一版本配置下必须命中同一 `provider_key` |
| 容错机制 | L2 | 配置缺失/参数缺失时 100% 返回可分类错误码（不抛 500） |
| 可观测性 | L2 | start 失败场景日志覆盖率 100%，包含 `provider/service_provider/reason` |
| 可维护性 | L2 | list/dict 双配置结构均有自动化回归测试，防回归门禁必跑 |
| 安全性 | L1 | 延续现有 JWT 签发与校验，不新增敏感面，不降低当前安全基线 |
| 可用性 | L1 | 不新增可用性架构目标，保持当前单实例开发态可运行 |

## 逐增量 NFR 分析

### Increment 1: GitLab 路由修复薄切片

#### NFR 类别: 性能
- **等级**: L2 - 标准
- **量化目标**: `GET /api/accounts/gitlab/oauth/start/` 服务端处理耗时 P95 <= 300ms，P99 <= 800ms（不含外部跳转页面加载）
- **质量场景**: QS-01

#### NFR 类别: 一致性
- **等级**: L2 - 标准
- **量化目标**: 相同输入命中结果确定性 100%（`provider_key` 不漂移）
- **质量场景**: QS-02

#### NFR 类别: 安全性
- **等级**: L1 - 基础
- **量化目标**: 非法/过期/篡改 token 请求全部拒绝，拒绝率 100%，不泄露密钥信息

### Increment 2: 双结构兼容加固

#### NFR 类别: 一致性
- **等级**: L2 - 标准
- **量化目标**: list/dict 两种输入结构解析后关键字段一致率 100%（`provider_key/allowedHost/client_id/redirect_uri`）
- **质量场景**: QS-03

#### NFR 类别: 可维护性
- **等级**: L2 - 标准
- **量化目标**: 新增兼容逻辑由单测覆盖，关键分支覆盖率 >= 90%
- **质量场景**: QS-04

### Increment 3: 可观测与回归守卫

#### NFR 类别: 容错机制
- **等级**: L2 - 标准
- **量化目标**: 已知故障（配置缺失、参数缺失、token 校验失败）全部映射到稳定错误分类，无 500
- **质量场景**: QS-05

#### NFR 类别: 可观测性
- **等级**: L2 - 标准
- **量化目标**: 失败日志必须带 `provider/service_provider/reason/trace_id`，覆盖率 100%
- **质量场景**: QS-06

### Increment 4: 健康信号增强

#### NFR 类别: 可用性
- **等级**: L1 - 基础
- **量化目标**: 健康接口继续可用；新增 provider 摘要不影响现有健康检查成功率

#### NFR 类别: 可观测性
- **等级**: L2 - 标准
- **量化目标**: 健康响应中可看到 GitLab provider 配置计数，空配置可在 1 次探测内识别
- **质量场景**: QS-07

## 领域模型影响

| NFR 决策 | 模型影响 | 对应 DDD 动作 |
|----------|---------|-------------|
| 一致性 L2（路由确定性） | provider 路由规则需具备确定性和值对象语义 | 在 DDD 中将 `provider/service_provider/allowedHost` 建模为不可变值对象，路由服务仅做纯决策 |
| 容错 L2（分类错误，不抛 500） | 路由决策需显式表达“拒绝原因”而非异常泄漏 | 在领域服务返回 `resolved/rejected(reason)` 结果对象，基础设施层映射到 HTTP 错误路径 |
| 可观测性 L2（失败可诊断） | 需要可追踪的领域事件或结构化结果 | 在 DDD 中增加 `AuthorizeRouteResolved/Rejected` 领域事件，统一携带 reason/trace 元数据 |
| 可维护性 L2（双结构兼容） | 领域层与配置读取解耦，避免格式变化污染业务规则 | 建立配置仓储接口，解析逻辑放基础设施层，领域服务只消费标准化配置实体 |
| 安全 L1（保持基线） | 本轮不引入新授权模型 | DDD 阶段不扩展新的鉴权聚合，沿用现有 bridge token 边界 |

## 权衡与边界

### 取舍
- 选择一致性 L2（确定性路由）而非更高等级分布式一致性，因为当前场景是单请求内决策，不需要跨服务强一致事务。
- 选择可观测性 L2（可诊断）优先于可用性 L3 架构加固，先确保“能快速定位与修复”。

### 明确不做什么
- 不在本增量引入多节点高可用或跨地域容灾（可用性保持 L1）。
- 不在本增量引入新持久化模型或复杂权限模型（安全保持 L1）。
- 不追求极致性能目标（如 P99 < 100ms），以正确性和可诊断性优先。

### 升级触发条件
- 当 OAuth 授权流量达到峰值 >= 日均 5 倍，且 P95 超过目标时，性能从 L2 升级到 L3，考虑缓存与读写分离优化。
- 当服务从单实例走向多实例并承担外部承诺 SLA 时，可用性从 L1 升级到 L3，补充健康探测与故障转移策略。
- 当审计合规要求提升（如 SOC2 证据链）时，可观测性从 L2 升级到 L3，增加可追溯审计事件持久化。

## 跳过声明

- 可伸缩性: 跳过。当前增量主要是配置解析与路由修复，无新增高吞吐处理链路。
- 合规与隐私: 跳过。本增量不新增个人数据处理路径与数据跨境行为。
