# 功能意图：资源订单展示号带租户基因，主键仍为订单 Snowflake

## 意图

新单展示号为 `ORD-{UTC日期}-{tenantId}-{snowflakeId}`。用户/客服只贴该号码即可得到租户与订单主键，不必另交租户 ID。系统身份与 URL 仍用末段 Snowflake `id`。分片按 `tenant_id` 列。

## 角色

- 租户成员 / 管理员：列表看到四段订单号；链接仍是 `/tenant/{tid}/billing/orders/{id}/`
- 客服 / 系统管理员：只拿到展示号时解析第 3 段为租户、第 4 段为 `id`，再走既有租户订单页
- 咨询用户：不需要额外提供租户 ID

## 行为

1. 新单 `order_number` = `ORD-{UTC yyyyMMdd}-{tenantId}-{id}`，末段等于主键 `id`。
2. 分配不查询当日最大序号。
3. URL 仍为 `/tenant/{tid}/billing/orders/{id}/`。
4. 存量 `ORD-YYYYMMDD-NNN` 与 ADR-0017 三节号继续展示，不改写。
5. 凭四段号定位：解析后 `WHERE tenant_id=? AND id=?`，行上租户必须与基因一致。
6. 租户面加载同样带 `tenant_id` 谓词。

## 非目标

- 不提供匿名公网「只凭订单号返回订单详情」API。
- 不改变微信支付 `out_trade_no`。
- 不把租户基因写入 64-bit Snowflake PK。
- 不把租户内短序号作为全局唯一键。
- 不改写存量号码。

## 业务意图 → 事件对照

**无对应新事件（书面例外）**：只改变展示号派生与只读解析；下单仍用既有日志 `resource_order_created`。

| 业务意图 | 事件名（过去式） | 发布点 | 消费者/副作用 | 例外理由 |
|---------|----------------|--------|--------------|---------|
| 生成带租户基因的全局展示号 | — | — | — | 无新业务状态 |
| 凭展示号解析租户并定位订单 | — | — | — | 只读 |
