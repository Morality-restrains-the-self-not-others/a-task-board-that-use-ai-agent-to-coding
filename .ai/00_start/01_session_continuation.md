# 会话中断与「继续」请求

## 背景

因网络或服务限制，上一轮智能体应答可能在执行到一半时中断；用户往往会发送简短的「继续」类消息。本节约束**恢复执行时的默认做法**，以降低重复劳动、冗余推理和无效长耗时操作。

## 适用范围

- 用户仅输入「继续」「go on」「接着做」等简短续接，或未重复完整需求。
- 上一轮流式输出在中间截断，工具调用可能未全部完成。

## 核心原则：**先校准工作区事实，再接续动作**

不可用「从头复述需求→重新大范围探索」代替对当前进度的对齐。

## 推荐执行顺序

1. **恢复任务意图（低成本）**
   - 优先从**当前会话可见的对话历史**中读取：上一轮承诺的未完成项、明确的「下一步」、正在修改的路径。
   - 若历史中目标不清，再用 **`git status` / `git diff`** 与必要时**定向读取近期改动文件**，推断剩余工作；不要用全文模糊搜索顶替「看 diff」。

2. **断点直进**
   - 若上一轮已明确下一步具体操作（例如某文件某函数、某条命令的余下参数），**直接执行该步**，跳过需求复述和重复方案讨论。
   - 仅当 workspace 呈现的结果与记忆中的「本应完成」明显不一致时，再扩大核对范围。

3. **避免重复 expensive 操作**
   - 不向用户索取其已在上一轮提供且仍存在于聊天中的约束或代码片段——除非你无法从上下文或文件中恢复。
   - 不盲目重跑上一轮已成功完成且未改前提的长命令（如整仓测试、重装依赖）；按需改为**针对变更范围的验证**。
   - 若同类搜索/读写在上轮已做过且文件未变化，改用**精读 diff 或未读段落**而非再次全文件搜索。

4. **上一轮输出丢失时的补丁**
   - 若记忆中的中间结论不可用，用 **最小粒度**工具调用（单行/局部 `read`、`grep`、小范围检索）补缺，而非整目录反复扫。

5. **事实优先级**
   - 当用户描述与本仓库 **`git`/工作区/`read` 所见**冲突时，以工作区为准，并简要说明再修正。

## 与「从零开始对话」的差别

从零开始需要先对齐需求；**「继续」默认同一会话下推进同一任务**，开篇动作应是**状态校准 + 完成余下工作**，而非重新写一篇「理解你的需求如下」——除非历史中已无法识别任何目标任务。
