# 提示词管理指引

> **SSOT**：仓库根目录 `.ai/` 为细则唯一正文；`task2app/.ai` 为指向根 `.ai` 的符号链接。总索引见 `.ai/project_rules.md`。Cursor `.cursor/rules/*.mdc` 为会话加载薄封装，勿与 `.ai` 双份维护长文。

## 1. 提示词存放结构

### 1.1 顶层结构
- 提示词按照开发职能分类存放在对应的目录中
- 每个职能目录下可创建多个提示词文件，文件名格式：`{序号}_{提示词主题}.md`
- 序号建议使用两位数，便于排序和查找

### 1.2 职能目录
```
.ai/                         # 唯一细则 SSOT（见 .ai/README.md）
├── project_rules.md         # 金字塔总索引
├── 00_start/
├── 01_project_constraints/
├── 02_documentation/
├── 03_technical_implementation/
├── 04_frontend_development/
├── 05_testing_quality/
├── 06_execution_monitoring/
├── 07_togaf_project_management/
├── 08_prompt_management/
├── 09_failure_experience/
├── 10_software_design_philosophy/
└── 11_ai_development/

.cursor/rules/               # Cursor 会话元规则（薄封装 / alwaysApply）
├── ai-rules-loader.mdc
├── project_rules.md         # -> ../../.ai/project_rules.md
└── *.mdc
```

### 1.3 职能文件内部结构
- 当某个职能文件内容过大时，可进一步拆分为子主题文件
- 子主题文件存放在对应职能目录的子目录中
- 例如：
  ```
  .ai/04_frontend_development/
  ├── 00_frontend_development.md        # 前端开发规范主文件
  ├── component_design/                 # 组件设计子目录
  │   ├── 01_component_naming.md        # 组件命名规范
  │   └── 02_component_styling.md       # 组件样式规范
  └── workflow/                         # 工作流子目录
      ├── 01_requirement_analysis.md    # 需求分析流程
      └── 02_ui_implementation.md       # UI实现流程
  ```

## 2. 提示词引用方式

### 2.1 上层文件引用
- 上层文件（如主规范文件）仅存放提示词的文件路径
- 使用 Markdown 链接格式引用具体提示词文件
- 例如：
  ```markdown
  # 前端开发规范
  
  ## 组件设计
  - 组件命名规范：[组件命名](./component_design/01_component_naming.md)
  - 组件样式规范：[组件样式](./component_design/02_component_styling.md)
  ```

### 2.2 AI工具按需加载
- AI工具应支持按需加载提示词，仅加载当前任务所需的提示词文件
- 加载逻辑：根据当前任务类型，定位到对应的职能目录，加载相关提示词文件
- 避免一次性加载所有提示词文件，减少token消耗

## 3. 提示词文件管理

### 3.1 文件大小控制
- 单个提示词文件必须不超过256行
- 当文件超过256行时，必须进行分裂，采用类似数据库B+树的结构：
  1. 抽象层：提取核心规则和通用概念，形成上层抽象文件
  2. 实现层：将具体实现细节拆分为多个子文件
  3. 调整引用关系：上层文件仅存放对子文件的引用，AI工具按需加载
- 拆分原则：
  - 抽象层：包含核心原则、通用规范和引用关系
  - 实现层：按照功能模块、流程阶段或主题领域进行细分
  - 确保每个子文件聚焦于单一主题，便于维护和使用

### 3.2 文件名规范
- 文件名格式：`{序号}_{提示词主题}.md`
- 序号：使用两位数，便于排序和查找
- 提示词主题：简洁明了，反映文件内容的核心主题
- 例如：`01_component_naming.md`、`02_database_design.md`

### 3.3 内容组织
- 每个提示词文件应围绕一个核心主题展开
- 内容必须符合 MECE 原则（Mutually Exclusive, Collectively Exhaustive）：
  - 相互独立：各部分内容之间没有重叠，边界清晰
  - 完全穷尽：涵盖该主题下的所有相关内容，没有遗漏
- 内容应结构清晰，使用适当的标题层级
- 关键信息可使用列表、加粗等格式突出显示
- 组织逻辑：按照功能模块、流程顺序或重要程度进行结构化排列

## 4. 提示词更新流程

### 4.1 更新规则
- 当需要修改提示词时，直接修改对应的提示词文件
- 避免在主文件中直接修改提示词内容
- 修改后应检查引用关系是否正确

### 4.2 版本控制
- 提示词文件的修改通过Git进行版本控制
- 重要修改应在提交信息中说明修改内容和原因

## 5. 提示词使用建议

### 5.1 按需加载
- AI工具应根据当前任务类型，仅加载相关的提示词文件
- 例如：进行前端组件开发时，仅加载`frontend_development/`目录下的相关提示词
- 当任务属于“功能意图实现”时，必须加载：[意图驱动开发工作流规范](./01_intent_driven_development.md)

### 5.2 模块化设计
- 提示词应采用模块化设计，每个模块负责特定的功能或场景
- 便于组合使用，适应不同的任务需求

### 5.3 定期优化
- 定期检查提示词文件，移除过时或不再使用的内容
- 合并重复或相似的提示词
- 更新提示词以适应项目需求的变化

### 5.4 智能体开发规则显示
- 当使用智能体开发时，应该明确显示使用了哪些智能体规则文件
- 显示方式：在智能体执行日志或输出中列出所加载和使用的规则文件路径
- 显示内容：包括规则文件的完整路径、版本信息（如果有）和加载时间
- 目的：提高开发过程的透明度，便于调试和问题定位

### 5.5 意图驱动交付顺序
- 功能任务默认采用意图驱动流程：先写功能意图，再写测试意图，再改代码，再写测试并验证
- 意图文档统一放在 `docs/intents/` 下，按金字塔层级目录组织
- 功能意图使用 `.intent.md` 后缀，测试意图使用 `.test-intent.md` 后缀，且必须同名异后缀并排存放
- **业务意图 → 业务事件**：服务端业务意图出现时，必须向消息队列投递对应业务事件；意图文档须含「意图 → 事件 → 发布点」对照（细则见 [意图驱动开发工作流规范](./01_intent_driven_development.md)）

## 6. 示例结构

### 6.1 示例1：主文件引用
```markdown
# 技术实现要求

## 数据库设计
- 数据库命名规范：[数据库命名](./database/01_database_naming.md)
- 表结构设计：[表结构设计](./database/02_table_design.md)
- 索引设计：[索引设计](./database/03_index_design.md)

## API设计
- API命名规范：[API命名](./api/01_api_naming.md)
- 请求响应格式：[请求响应格式](./api/02_request_response.md)
```

### 6.2 示例2：子主题文件
```markdown
# 数据库命名规范

## 1. 数据库名称
- 数据库名称应使用小写字母
- 多个单词之间使用下划线分隔
- 示例：`saas_project_db`

## 2. 表名称
- 表名称应使用小写字母
- 多个单词之间使用下划线分隔
- 应体现表的业务含义
- 示例：`user_account`、`order_info`

## 3. 字段名称
- 字段名称应使用小写字母
- 多个单词之间使用下划线分隔
- 应体现字段的业务含义
- 示例：`user_id`、`create_time`
```

## 7. 总结

- 提示词按照职能分类存放，便于管理和查找
- 上层文件仅存放引用，AI工具按需加载，减少token消耗
- 单个提示词文件不宜过大，及时拆分避免浪费
- 定期维护和优化提示词，确保其有效性和相关性

遵循本指引可以有效管理提示词，提高AI工具的使用效率，减少不必要的token消耗，同时便于团队协作和维护。
