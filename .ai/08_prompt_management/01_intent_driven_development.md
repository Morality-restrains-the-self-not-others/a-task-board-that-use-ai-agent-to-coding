## 规则分类

### 核心规则
> 面向功能实现的意图到代码闭环规则，必须严格遵守

#### 业务意图 → 业务事件 → 消息队列（强制）
- 描述：每当一个**业务意图**出现（用例被触发、命令被接受、功能意图中的服务端业务动作），必须向消息队列投递一个**对应的业务/领域事件**，不得以同步直调跨边界副作用替代。
- 适用场景：所有会改变系统事实、或触发跨聚合/跨服务/异步副作用（邮件、SSE、下游协作等）的服务端业务意图。
- 优先级：强制
- 规则：
  1. **一对一默认映射**：每个上述业务意图至少对应一个业务事件（复合意图可拆多个事件；禁止「有意图无事件」）。
  2. **投递时机**：在意图所属一致性边界内的状态变更完成后发布（应用服务编排末尾 / 聚合记录事件后由基础设施投递）；经 `EventBusPort`、`send_event`、`PublishEvent` 等既有端口进入 MQ（开发模式可为内存队列，见 `05_best_practices.md`）。
  3. **文档对照**：`.intent.md` 必须包含「意图 → 事件名（过去式）→ 发布点（服务/用例）→ 消费者（若已知）」对照表；推荐含「MQ类型/契约」列。`.test-intent.md` 须覆盖「意图发生时事件被投递」的断言或用例行。CI：`task2app/scripts/ci/check_ddd_bdd_compliance.py` 第一层校验对照表存在；第二层对有事件行抽检 publish/契约证据（token 索引缓存于 `task2app/.cache/intent_publish_corpus/`）。非 MQ 路径须「证据豁免」并登记 `docs/intents/_meta/publish_evidence_exempt.yaml`（含 `future_mq_contract`，改走 MQ 后删除）。存量回填/精修：`runAll/scripts/backfill_intent_event_tables.py`、`runAll/scripts/refine_intent_event_tables.py`。
  4. **消费侧对齐**：一个消费脚本只处理一个明确业务意图；命名遵循 `序号_业务意图.是否激活.py`（见 Kafka 最佳实践）。
  5. **例外（须书面标注）**：纯查询/只读、纯前端无服务端状态变更可不发事件；须在意图文档写明「无对应事件」及理由。禁止以「暂时同步调用更简单」作为例外理由。同步 HTTP 直写等非 MQ 路径若保留事件行，须在例外理由写「证据豁免：…」并登记 `_meta/publish_evidence_exempt.yaml`。
  6. **与 DDD 关系**：事件契约属领域层；MQ 适配器属基础设施。细则见 `.ai/03_technical_implementation/09_domain_driven_design.md`。

#### 意图目录与金字塔组织
- 描述：每次收到“功能意图指令”时，必须先在 `docs/intents/` 下创建或更新对应文档，并按金字塔结构组织内容。
- 适用场景：新增功能、功能改造、功能修复、流程重构。
- 优先级：高
- 规则：
  1. 功能意图文档必须使用 `.intent.md` 后缀。
  2. 同名测试意图文档必须使用 `.test-intent.md` 后缀，并与功能意图文档放在同一目录。
  3. 功能意图文档内容必须按金字塔结构组织：`背景与目标 -> 范围与边界 -> 约束与风险 -> 验收标准 -> 实施计划`；其中须含上述「意图 → 事件」对照（或显式例外说明）。
  4. 测试意图文档内容必须与功能意图逐项映射：`测试目标 -> 测试分层 -> 用例矩阵 -> 数据与环境 -> 通过标准`。

#### 意图命名与目录层级
- 描述：意图目录需体现“从抽象到具体”的层级，便于快速定位与复用。
- 适用场景：所有意图文档创建与维护。
- 优先级：高
- 规则：
  1. 目录结构：`docs/intents/{一级域}/{二级子域}/`。
  2. 文件名前缀使用递增序号：`NNN_主题.intent.md` 与 `NNN_主题.test-intent.md`。
  3. 同一主题的功能意图与测试意图必须同名异后缀，禁止脱钩。
  4. 若已存在同主题文档，应优先更新而非重复创建。

#### 执行顺序（强制）
- 描述：实现必须遵循“先意图、后代码、再测试、最终验证”的闭环顺序。
- 适用场景：所有功能开发任务。
- 优先级：高
- 规则：
  1. 先产出/更新功能意图文档。
  2. 基于功能意图产出/更新测试意图文档。
  3. 按功能意图修改项目代码。
  4. 按测试意图生成或更新测试代码。
  5. 运行测试并验证功能意图是否被正确实现。
  6. 如验证失败，必须回到意图与实现同步修订，直至通过。

### 最佳实践
> 帮助提高意图文档质量和交付效率

#### 意图与实现一致性维护
- 描述：实现完成后，意图文档应反映最终行为而非初稿设想。
- 适用场景：功能开发结束前。
- 优先级：中
- 建议：
  1. 验证通过后回写关键实现决策到 `.intent.md`。
  2. 在 `.test-intent.md` 中记录已覆盖与未覆盖项，避免假覆盖。

## 规则冲突处理
- 当规则冲突时，遵循以下优先级：
  1. 核心规则 > 最佳实践 > 风格指南
  2. 文件级规则 > 目录级规则 > 全局规则
  3. 新版本规则覆盖旧版本规则
