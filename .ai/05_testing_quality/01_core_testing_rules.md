## 规则分类

### 核心规则

#### 提交时随机单元测试与遗留债 10% 修复
- 描述：每次 Git 提交须经 pre-commit 执行 monorepo 随机单元测试门禁。若抽测发现遗留失败文件数为 N，同次提交至少修复 `max(1, ceil(N×0.10))` 个并复跑通过；余债写入 `.learnings/UNIT_TEST_DEBT.md`。暂存触及的单测须 100% 通过。禁止 `--no-verify`。与「监控机制：提交前相关测试 100%」叠加时：对本规则定义的遗留随机发现适用 10% 配额，其余仍须通过。
- 适用场景：所有提交；Agent 代提；撞上随机遗留失败时
- 优先级：强制
- 详细内容：请参考 [提交时随机单元测试与遗留债 10% 修复](../01_project_constraints/28_commit_random_unit_test_debt_fix.md)

#### 单元测试定位规则
- 描述：当出现某个逻辑没有验通时，应该对这个逻辑的每个单独的一环进行单元测试，以便缩小处理的复杂度，快速定位到哪里出现了问题。等问题修复后，需要对整体逻辑进行一次验证，以确保整体逻辑没有被修改
- 适用场景：当系统逻辑出现验证失败或异常时
- 优先级：高

#### DDD测试原则
- 描述：测试**必须**符合 DDD 原则；除非该测试专门验证外部依赖行为，否则不得绕过领域边界或把基础设施细节当作领域断言的依据
- 适用场景：当编写或修改测试用例时
- 优先级：强制

#### BDD 先测后写规则
- 描述：撰写功能时**必须**按照 BDD 方式进行，先编写测试用例，再编写具体的业务职能；当测例全部通过时，业务职能即视为能够正确跑通。禁止先写业务再补测，应严格遵循「测例先行」的顺序；并与 CI「业务与测例同批变更」门禁一并遵守（见 `scripts/ci/README_DDD_BDD_COMPLIANCE.md`）
- 适用场景：所有新功能开发、业务逻辑实现、API 接口开发、领域服务开发
- 优先级：强制
- 详细内容：请参考 [BDD 开发流程规范](./04_bdd_development_workflow.md)

#### Playwright与Chrome DevTools MCP配合使用规则
- 描述：使用 playwright 时需要配合 Chrome DevTools MCP 一起使用，以提高测试效率和调试能力
- 适用场景：当使用 playwright 进行测试时
- 优先级：高

#### Playwright 通过 9222 端口连接非沙盒 Chrome 规则
- 描述：使用 Playwright 时，应通过 **9222** 端口的 Chrome DevTools Protocol（CDP）连接**已由外部启动**的 Chrome，即「非沙盒」语境下的本机 Chrome 实例（使用独立用户数据目录、非 Playwright 默认 `launch()` 拉起的隔离 Chromium），而不是仅依赖内置 Chromium 的默认沙盒启动方式。测试侧使用 `connectOverCDP`（如 `http://127.0.0.1:9222` 或 `http://localhost:9222`）接入；浏览器侧需预先以远程调试端口启动，例如 `--remote-debugging-port=9222` 并指定 `--user-data-dir`（工作区根目录可参考 `runDebugChrome.sh`）。在 Linux 容器等需要关闭浏览器沙盒的环境，启动 Chrome 时可按需附加 `--no-sandbox`，仍保持 **9222** 为 CDP 接入端口。
- 适用场景：使用 Playwright 编写、运行或调试端到端测试；智能体通过 Playwright 操作页面时
- 优先级：高

#### Playwright 动态页面与智能体执行要点
- **描述**：在遵守 **9222 CDP 连接** 与「Chrome DevTools MCP 配合」等既有规则前提下，对 **SPA / 异步渲染** 页面编写或调试 Playwright、或由智能体驱动浏览器时，采用「先稳定、再侦察、后断言/操作」的顺序，减少脆性选择器与竞态失败。
- **适用场景**：端到端测例编写与维护；Agent 通过 Playwright 或 MCP 探查动态 UI
- **优先级**：高
- **规则**：
  - **静态 vs 动态**：若页面主要为静态 HTML 或可从源码可靠得到选择器，可直接基于源码与稳定 `data-testid` 等编写；否则按动态应用处理。
  - **等待就绪再侦察**：在动态页上，在截取全页图、导出 DOM 或枚举可操作元素之前，应先等到网络与主框架稳定（例如 `waitForLoadState('networkidle')` 或与该路由匹配的 `waitForURL` / `waitForSelector`）；**禁止**在首屏脚本尚未完成时凭猜测硬写易变 CSS。
  - **侦察—再行动**：优先基于**渲染后** DOM 确定 `role` / `text` / 可访问名 / 稳定测试钩子，再落实点击与断言。
  - **脚本与包装命令**：本仓库要求测试旁配备 `fileName.sh`（见下「测试文件可执行性规则」）；若脚本或项目提供的包装 CLI 支持 `--help`，智能体应**先读帮助再调用**，将冗长实现当作黑盒执行，避免把大段脚本内容读入上下文。

#### 测试文件存储规范
- 描述：所有测试文件必须放置在专门的目录中，避免与项目业务代码混合
- 适用场景：所有测试文件的创建和管理
- 优先级：高
- 规则：
  - 后端单元测试：应放在`test`或`tests`目录中，按照模块或功能进行组织
  - 集成测试：应放在专门的`integration_tests`目录中
  - 端到端测试：应放在专门的`e2e`或`end_to_end_tests`目录中
  - 测试目录结构应清晰反映测试类型和覆盖范围

#### 测试分层隔离规则
- 描述：领域模型测试、基础设施测试与端到端测试应严格分开，不得混合在同一目录或文件中，以便独立运行、维护和定位问题
- 适用场景：所有测试文件的组织、创建和维护
- 优先级：高
- 规则：
  - **领域模型测试**：测试纯领域逻辑（聚合、实体、值对象、领域服务等），不依赖数据库、消息队列、外部 API 等基础设施；应放在 `tests/domain/` 或按领域划分的 `tests/{domain_module}/` 目录，使用 Mock/Stub 隔离外部依赖
  - **基础设施测试**：测试数据库、消息队列、云厂商 SDK、外部 API 等基础设施的集成与适配；应放在 `tests/infrastructure/` 或 `integration_tests/infrastructure/` 目录，可依赖真实或测试环境的外部服务
  - **端到端测试**：测试完整业务流程，从用户界面到后端全链路；应放在 `e2e/`、`end_to_end_tests/`、`playwright/front_project/tests/` 或 `playwright/saas_ai_provider/tests/` 等专门目录
  - 同一测试文件内不得同时包含领域模型测试和基础设施测试；端到端测试应独立于前两者
  - 执行时可按分层选择性运行：领域模型测试可频繁快速执行，基础设施与端到端测试可按需或流水线阶段执行

#### 测试文件命名规范
- **描述**：不同类型的测试文件需要使用不同的文件后缀，以便于识别和使用适当的测试运行器
- **适用场景**：所有测试文件的创建和命名
- **优先级**：高
- **规则**：
  - Playwright 端到端测试：使用 `.playwright.test.js` 后缀
  - 单元测试：使用 `.unit.test.js` 后缀
  - 集成测试：使用 `.integration.test.js` 后缀
  - 其他测试：使用 `.test.js` 后缀
  - 测试文件命名应清晰反映测试的功能和范围

#### 测试文件可执行性规则
- **描述**：所有测试文件必须在同一目录下配备对应的 `fileName.sh` 脚本，运行该脚本即可直接执行该测试文件
- **适用场景**：所有测试文件的创建和管理
- **优先级**：高
- **规则**：
  - **统一要求**：每个测试文件旁应有一个同名的 `.sh` 脚本（如 `test_foo.py` 对应 `test_foo.sh`），脚本运行后直接执行该测试文件
  - **命名规范**：脚本名为 `{测试文件名去掉扩展名}.sh`，与测试文件置于同一目录
  - **后端测试**：创建 Python 单元测试（`test_*.py`）时，必须同时创建对应的 `test_*.sh` 脚本，脚本负责激活单元测试环境并调用 pytest 执行该测试文件
  - **前端测试**：创建 Playwright 等前端测试时，必须同时创建对应的 `fileName.sh` 脚本，脚本负责执行该测试文件，并把测试结果输出到 commitResult 中
  - 测试脚本应该能够直接运行（`./fileName.sh`），无需依赖外部测试运行器（虽然也可以通过 pytest/npx 等直接执行测试文件）
  - 确保测试脚本在不同环境中都能正常执行

#### 单元测试
- 描述：定义单元测试的设计、执行和维护规范
- 适用场景：所有单元测试开发和执行
- 优先级：高
- 规则：
  - 开发原则：执行任务前，应该先按照意图修改或创建一个单元测试，然后才开始执行任务，并不断的测试直到单元测试通过时，任务完成
  - 测试优先级：添加单元测试时，应该先从业务领域开始添加单元测试，确保核心业务逻辑的正确性
  - 执行流程：
    1. **任务分析**：明确任务目标（bug修复、功能开发等）
    2. **测试设计**：根据任务意图，设计并创建/修改对应的单元测试
    3. **测试执行**：运行新创建的测试，确认其初始状态为失败（预期）
    4. **代码实现**：编写/修改代码以实现任务目标
    5. **测试验证**：再次运行测试，确保测试通过
    6. **回归测试**：运行相关模块的所有测试，确保没有引入新问题
  - 执行时机：
    - 每次开始任务前，必须创建/修改对应的单元测试
    - 每次完成功能开发、修复bug或修改view.py文件后，必须运行单元测试
  - 测试要求：
    - 项目生成完成后，为每个用例撰写单元测试
    - 单元测试中有对应的setup和teardown流程
    - 测试用例应覆盖正常流程、边界情况和异常情况
  - 命名规范：以/tests/`view`_test/`cls`_`method`_test.py的格式命名
  - 存储位置：所有单元测试必须放在专门的`test`或`tests`目录中，避免与业务代码混合
  - 维护要求：当`view`.py中的内容变化时，对应的测试也应该调整
  - 监控机制：每次提交代码前，必须运行相关测试，确保测试通过率100%
  - 执行命令：
    - 使用pytest运行view_test目录下的测试：在Saas_project目录下运行`DJANGO_SETTINGS_MODULE=saas_project.settings python -m pytest /tests/accounts/view_test/ --tb=short`
    - 必须添加`-v`参数查看详细测试结果，确保打印当前运行的单元测试名称
  - 测试调试：
    - 如果测试失败，先检查测试代码本身是否正确，然后再检查被测试的功能代码
    - 查看详细错误信息，定位问题所在

#### 测试验证标准
- 描述：定义测试验证的标准和要求
- 适用场景：所有测试验证过程
- 优先级：高
- 规则：
  - 所有单元测试必须通过，测试通过率达到100%
  - 代码覆盖率要求：单元测试覆盖率不低于95%，集成测试覆盖率不低于90%
  - 运行测试后需检查测试报告，确保没有失败的测试用例

## 规则冲突处理
- 当规则冲突时，遵循以下优先级：
  1. 核心规则 &gt; 最佳实践 &gt; 风格指南
  2. 文件级规则 &gt; 目录级规则 &gt; 全局规则
  3. 新版本规则覆盖旧版本规则
