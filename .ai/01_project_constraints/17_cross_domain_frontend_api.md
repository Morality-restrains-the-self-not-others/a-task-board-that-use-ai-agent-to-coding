# 异域部署：前端站点与 API 分域名

## 规则分类

### 核心规则

#### 部署前提（设计必纳）

- **描述**：本仓库产品形态中，**用户访问的 Web 前端**与 **HTTP(S) API 服务**可部署在**不同域名**（含不同子域、不同一级域或不同端口在浏览器同源策略下亦视为跨源）。凡涉及鉴权、会话、请求构造、回调与安全的方案，须在设计与实现阶段**显式**按跨源场景评估，禁止默认「前后端同站」隐含假设。
- **适用场景**：新接口与鉴权流、Cookie/Token 策略、OAuth/SSO 回调、上传下载、WebSocket/SSE、支付跳转、Webhook、开放 CORS、内容安全策略（CSP）、第三方脚本与埋点、Playwright 与 E2E 基地址配置等。
- **优先级**：高

##### 设计与实现检查要点（非穷举）

- **CORS**：浏览器发起的跨源请求须配置允许的 `Origin`、方法与头；若使用 `credentials`（Cookie 或 `Authorization` 与 Cookie 并存等），须与 `Access-Control-Allow-Credentials`、具体允许的源（禁止与通配 `*` 误配）一致；预检（OPTIONS）路径与中间件顺序须可维护。
- **Cookie**：`SameSite`、`Secure`、`Domain` 与前端站点域关系须一致；跨站或跨子域场景下区分「第一方会话」与「第三方上下文」限制（如 CHIPS/分区 Cookie 政策演进），避免依赖在异域下必然失效的假设。
- **CSRF 与双重提交**：同站 CSRF 令牌模式在异域下可能不适用或需改为 Token 头、自定义头配合 CORS 等经评审的方案。
- **重定向与回调 URL**：OAuth、支付、邮件内链接、App 深度链接等须使用**可配置**的绝对 URL 列表，区分前端入口域与 API 域，禁止写死单一主机。
- **客户端基地址**：前端 HTTP 客户端、上传、SSE/WebSocket 的 base URL 须来自配置或环境变量，与静态资源部署域解耦。
- **反向代理与网关**：若生产路径经网关聚合域名，文档与本地开发仍须说明「浏览器视角下的真实 Origin」与「API 公网基 URL」是否分离。
- **测试**：E2E 与集成测试的 `BASE_URL`、API 根地址与 Cookie 域须与目标环境一致；避免仅在「同源本地联调」下通过而线上异域失败。

### 最佳实践

- 在 `docs/intents/`、ADR 或接口说明中，对涉及浏览器侧的请求，注明**前端 Origin** 与 **API 基 URL** 是否分离及鉴权载体（Cookie / Bearer / 混合）。
- 新增依赖「同站」能力的库或中间件前，先对照本节做兼容性核对。
