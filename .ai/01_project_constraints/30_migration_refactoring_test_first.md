# 迁移/重构类指令——测试先行（元规则）

## 基本信息

- 版本：1.0.0
- 创建日期：2026-07-24
- 最后修改：2026-07-24
- 维护者：Trae AI 团队

## 背景（为何是元规则）

迁移（migration）与重构（refactoring）类操作的核心承诺是「**外部行为不变，内部结构优化**」。但在 AI 辅助开发中，常见反模式是：直接执行大规模代码改动 → 改后行为偏差 → 回滚或修补成本高 → 测试缺失导致无法验证一致性。

本规则要求：**在识别到迁移/重构意图后，必须先建立行为基线（测试），再执行改动，最后用同一测试集验证行为未退化。** 这是防御性工程实践在 AI 编码场景下的落地——用测试作为迁移的「安全网」。

## 规则分类

### 核心规则

#### 迁移/重构必须先写测试，确保前后行为一致

- **描述**：凡识别到用户指令中包含迁移或重构性质的意图，Agent 必须在执行任何代码改动之前，**先为受影响代码建立可验证的行为基线**（优先扩展现有测试；若无则写 characterization test / golden master test），确保改动前后外部行为一致。迁移/重构完成后，须用同一测试集验证通过，方可视为完成。
- **适用场景**：所有满足触发条件的用户指令（见下方「触发识别」）
- **优先级**：高
- **规则类型**：禁止忽略

## 触发识别

### 一级触发词（必定触发）

以下中英文关键词出现时，直接判定为迁移/重构类指令：

| 中文 | 英文 |
|------|------|
| 迁移 | migrate / migration |
| 重构 | refactor / refactoring |
| 重写 | rewrite |
| 搬迁 | relocate / move (含目录/模块搬迁) |
| 升级（框架/库/依赖大版本） | upgrade (major version) |
| 替换（组件/库/实现） | replace / swap out |
| 抽取（公共模块/共享库） | extract / extract to shared |
| 合并（模块/服务） | merge / consolidate |
| 拆分（模块/服务/大文件） | split / decompose |

### 二级触发模式（语义判定）

以下语义模式也视为迁移/重构，即便不含一级触发词：

- 「把 X 从 A 移到 B」
- 「将 X 改为用 Y 实现」
- 「用 Y 方案重新实现 X」
- 「把 A 服务/模块的 X 功能迁到 B」
- 「统一下层接口/统一 API 签名」
- 「修改数据模型并同步调整所有引用」
- 「批量重命名字段/函数/文件（影响 > 3 处调用点）」
- 「更换底层存储/中间件/通信协议」
- 「升级 Django/框架版本」（涉及 deprecated API 的批量修改）
- 「调整目录结构/模块组织」

### 不触发的情形（明确排除）

以下操作不属于本规则覆盖范围：

- 修复单一 bug（即便改动多行）
- 新增独立功能/接口（非对旧代码的改造）
- 纯粹代码格式化（仅 style/format，不改变逻辑结构）
- 添加日志/注释/文档
- 单文件小范围调整（< 20 行有效变更，且不改变接口签名）

## 执行流程

### 阶段一：识别与确认

1. Agent 收到用户指令
2. 对照「触发识别」判定是否命中
3. 命中后，在执行任何代码改动之前，进入阶段二
4. **若不确定是否触发**：宁可保守触发（多写测试无害），也不跳过

### 阶段二：建立行为基线

1. **定位受影响代码**：确定迁移/重构会触及的函数、类、模块、API 端点
2. **检查现有测试**：搜索对应测试文件
   - Django: `tests/` 目录、`test_*.py`
   - Go: `*_test.go`
   - 前端: `*.test.*`、`*.spec.*`、`*.playwright.test.*`
3. **评估覆盖充分性**：
   - ✅ 已有充分测试覆盖受影响接口 → 可直接进入阶段三
   - ⚠️ 测试存在但不充分 → 补充关键路径的缺失 case
   - ❌ 完全无测试 → 必须写 characterization test（特征测试/基线测试）
4. **写测试的原则**：
   - 测试**当前实际行为**，不是「期望行为」（即便当前行为有瑕疵，先记录再决定是否修复）
   - 覆盖迁移/重构会触及的**所有公开接口**（输入-输出契约）
   - 覆盖关键**边界条件**和**错误路径**
   - 使用项目已有的测试框架与约定（见 `.ai/05_testing_quality/`）

### 阶段三：执行迁移/重构

1. 执行代码改动
2. 改动过程中持续运行阶段二的测试（每次改动后立即验证）
3. 若测试失败：**立即修复**，不继续堆叠更多改动

### 阶段四：验证一致性

1. 运行**完整**测试套件（不仅阶段二的测试）
2. 确认：
   - 所有阶段二测试通过 ✅
   - 无新增测试失败 ✅
   - 若测试需要更新（API 签名有意变更等）：明确记录变更原因，更新测试并确保等价覆盖 ✅
3. 运行项目 CI 门禁（pre-commit、lint、行数门禁等）

### 阶段五：收尾

1. 将迁移/重构结果记录在 `.learnings/`（若涉及重要决策）
2. 若有新增测试文件：确认测试文件位置符合项目约定

## 测试类型指南

| 迁移/重构类型 | 推荐测试类型 | 说明 |
|-------------|------------|------|
| 代码搬迁（文件/目录重组） | 导入路径测试 + 现有测试全量 | 重点验证 import/reference 不broken |
| 函数/类重构（内部实现） | 单元测试 | 验证输入-输出契约不变 |
| API 重构（接口签名变更） | 集成测试 + API 契约测试 | 验证请求-响应格式兼容 |
| 数据库迁移（schema/字段变更） | Django migration 测试 + 数据完整性测试 | 验证 migration forward/backward + 数据不丢失 |
| 服务间功能搬迁 | 端到端测试 + API 契约测试 | 验证跨服务调用链路完整 |
| 框架升级 | 全量回归测试 | 重点验证 deprecated API 替换项 |
| 更换中间件/存储 | 集成测试 + 性能基线测试 | 验证功能等价 + 性能不退化 |
| 前端组件重构 | 组件测试 + Playwright 快照测试 | 验证渲染输出与交互行为一致 |

## 特殊情形处理

### 紧急修复与迁移交织

若用户明确标注「紧急/热修复」且同时涉及迁移性质操作：
- 先执行最小变更修复紧急问题（允许暂时跳过测试先行）
- **事后必须**补充测试并记录在 `.learnings/` 中

### 探索性重构（不确定目标形态）

若用户请求是「尝试重构 X，看看哪种方案更好」：
- 在每种方案尝试前，先基于当前行为写测试
- 用同一测试集验证各方案的兼容性
- 最终选定方案后，保留测试

### 行数门禁触发后的拆分

拆分大文件属于本规则覆盖范围（拆分 = 重构的一种形式）：
- 拆分前：用现有测试覆盖文件中的公开函数
- 拆分后：确保所有 import 路径更新，原测试仍然通过

## 质量检查清单

迁移/重构完成后，Agent 须自查：

- [ ] 是否在改动前写了测试（或确认现有测试充分）？
- [ ] 测试是否覆盖所有受影响的公开接口？
- [ ] 改动后所有既有测试是否通过？
- [ ] 是否有新增的测试来覆盖边界行为？
- [ ] 若有 API 签名变更：是否更新了所有调用方和对应测试？
- [ ] 是否运行了完整 CI 门禁？
- [ ] 若为数据库迁移：是否验证了 forward/backward？
