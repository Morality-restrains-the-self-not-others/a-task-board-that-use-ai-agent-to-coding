# 支付与 KYC 合规约束

## 基本信息
- 版本：1.1.0
- 创建日期：2026-04-21
- 最后修改：2026-08-22
- 维护者：项目团队

## 适用范围

凡涉及**收款、付款、充值、提现、订阅计费、钱包余额、退款、分账**等与资金或支付能力相关的功能设计、接口、数据模型、日志、第三方集成与测试，均须遵守本文件。与支付无直接关系的一般业务代码不在此列，但一旦与支付链路耦合，按本文件执行。

## 核心规则（必须遵守）

### 1. 合规优先与职责边界

- **法律依据**：实施前须明确适用司法辖区与监管要求（如反洗钱、支付机构/电子货币相关规则），在 `docs/` 或产品文档中记录**合规假设与待法务确认项**；不得在代码或注释中虚构已获监管批准。
- **不替代法务**：本仓库规则与实现不能替代专业合规/法务意见；涉及 KYC 政策、限额、黑名单策略等，以**书面合规结论**为准，代码须与之对齐并可追溯。

### 2. KYC 体系最低要求

- **身份层级**：为支付能力定义清晰的 **KYC 等级**（如未验证 / 基础 / 强化），并与**可执行操作**（单笔限额、日累计、提现、跨境等）绑定；等级变更须有**可审计记录**（谁、何时、由何依据、由何系统或人工触发）。
- **数据最小化**：仅收集与当前业务及监管要求**相称**的字段；禁止为「方便」扩大采集范围；敏感标识类数据须按项目安全规范加密存储与访问控制。
- **状态与生命周期**：KYC 申请、审核中、通过、拒绝、过期、需重验等状态须明确定义；拒绝与重验须向用户给出**合规允许范围内**的说明，避免泄露内部风控细节。

### 3. 第三方与卡/账户数据

- **PCI 与令牌化**：支付卡号、CVV、完整磁道等**不得**进入本应用自有数据库或日志；优先使用支付服务商提供的**托管页面、令牌化或官方 SDK**。
- **微信支付客户端**：凡调用微信支付 APIv3（下单、查单、退款、分账、回调验签/解密等），**必须**使用仓内 `sdk/wechatpay-go`（`github.com/wechatpay-apiv3/wechatpay-go`，服务 `go.mod` 须 `replace` 到该目录）；禁止社区 SDK、APIv2 自签或裸 HTTP。细则见 [59_wechatpay_go_sdk.md](./59_wechatpay_go_sdk.md)（ADR-0032）。
- **密钥与回调**：API 密钥、Webhook 签名密钥仅存放于安全配置与密钥管理约定处；所有支付回调必须**验签**并校验金额、币种、订单号等关键字段一致性。微信支付回调须走 SDK `core/notify`，禁止跳过验签。
- **供应商可审计**：选用具备合规资质的服务商时，在文档中记录**服务商名称、集成范围、数据出境/委托处理**等要点（按法务要求细化）。

### 4. 反洗钱与制裁（AML）挂钩

- **风险意识**：高风险场景（大额、异常频率、高风险地区/行业等）须预留**风控标记、人工复核或拒绝**的扩展点，不得写死「永远通过」。
- **名单筛查**：若业务要求，须使用规定的筛查渠道并保留筛查记录索引；不得自行维护「简化黑名单」替代正式流程而不经评审。

### 5. 日志、监控与隐私

- **禁止明文敏感信息**：日志、错误上报、前端控制台中**禁止**输出完整证件号、银行卡号、证件影像、完整生日等；必要时仅记录**脱敏片段或哈希/内部 ID**。
- **可观测性**：支付与 KYC 关键路径须具备**可追溯 request_id / 订单号**关联，便于事后审计与排障，且与 PII 展示分离。

### 6. 测试与数据

- **测试环境隔离**：集成测试使用**服务商测试模式 / 沙箱密钥**；禁止使用真实身份证件、真实银行卡做自动化测试。
- **fixture 数据**：测试数据须明显虚构，避免与真实个人重合；勿将含 PII 的导出文件提交到仓库。

## 最佳实践（建议）

- 在 `docs/flows/` 中维护支付与 KYC 相关流程图（与本项目文档规则一致），并在变更时同步更新。
- API 设计对 KYC 与支付错误返回**统一、可国际化**的用户文案，内部原因写入脱敏后的调试字段（参见技术实现中的 API 错误分层规范）。
- 对 KYC 与支付配置使用**显式配置项**与环境区分，避免隐式默认导致生产与测试行为不一致。

## 规则冲突处理

- 本文件与项目其他规则冲突时：**安全与合规相关条款优先**；具体冲突须在评审中显式记录决议。
