# 单库 / 单表单服务数据所有权（禁止跨服务直连共享表）

## 基本信息

- 版本：1.2.0
- 创建日期：2026-07-10
- 最后修改：2026-07-10
- 维护者：Trae AI 团队

## 背景（为何是元规则）

多服务若对同一数据库或同一数据表建立直连（共享连接串、跨服务 ORM Model、旁路 SQL），会导致：

- **所有权模糊**：schema 变更、迁移、索引与事务边界无法由单一责任方收敛
- **耦合与竞态**：隐式跨服务事务、锁争用、缓存不一致，故障面放大
- **演进受阻**：无法独立部署与扩缩；「改一张表」牵动多个进程与发布节奏

本规则将 **数据所有权** 固定为「一库或一表 ↔ 唯一拥有服务」，跨服务协作走 **服务接口转发**（HTTP/RPC/领域事件等），或通过 **迁表 / 拆表** 使每张表只归属一个服务，而非共享存储直连。

## 规则分类

### 核心规则

#### 单库 / 单表仅由一个服务访问

- **描述**：任意 **数据库实例（或逻辑库）**、以及其中任意 **数据表**，在运行时只允许由 **一个拥有服务（owner service）** 通过连接串 / ORM / 原生 SQL 等方式直接访问（读与写均适用）。其他服务 **禁止** 配置该库/表的连接、禁止复用其 Model/DAO、禁止旁路查询或写入。
- **适用场景**：
  - 新服务拆分、新表设计、跨进程读写既有表
  - monorepo 内多进程（如 Django SaaS、taskAuth、onlineServiceJS、relay 侧车等）访问持久化存储
  - 设计文档、价值流、DDD 限界上下文划分与仓储落点
  - Code review / 架构评审中发现「多服务共用一张表」或「共用一个库连接」
- **优先级**：高
- **规则类型**：禁止忽略（核心规则）

##### 所有权判定

| 项 | 要求 |
| --- | --- |
| 拥有服务 | 对该库或该表负 schema 与迁移责任的进程/部署单元；通常与限界上下文一致 |
| 粒度 | **优先按表**明确 owner；若整库仅服务一个上下文，可声明 **整库 owner** |
| 文档 | 新表或新库须在设计/意图文档或模块 README 中写明 owner；变更 owner 须同步文档与连接配置 |
| 禁止 | 两个及以上服务持有同一库/表的生产连接配置；「只读也算访问」——只读直连同样禁止 |

##### 发现多服务访问同一库/表时：两条合规路径（二选一或组合）

当已存在或即将出现「多个服务需要同一数据库或同一数据表」时，**禁止**继续共享直连。必须采用下列路径之一（可组合），使最终状态满足「一表仅一个服务直连」：

| 路径 | 做法 | 适用时机 |
| --- | --- | --- |
| **A. 服务转发** | 非拥有服务经拥有服务对外能力访问数据（见下节） | 表语义仍属当前 owner；他方只需读/写能力，不需持有 schema |
| **B. 数据表迁移出去** | 将表（或需共享的字段子集）迁到真正应拥有该数据的服务所管库/schema；原服务删除直连，改为调用新 owner 的 API/事件；或拆成各服务自有表 + 由 owner 同步的只读投影 | 表被「错放」在非主责服务；或多服务对同一实体有长期写需求，应重新划定 owner 后再迁表 |

**完成判据**：任意一张表在产品路径上只有一个服务持有其连接与迁移权；其余服务仅通过接口或事件协作。

##### 跨服务需要数据时：服务转发（路径 A）

当非拥有服务需要该表数据或需触发变更、且不迁表时，**必须**通过拥有服务对外暴露的能力访问，例如：

1. **同步**：HTTP/gRPC 等 API，由拥有服务校验、鉴权、读写本表后返回 DTO
2. **异步**：领域事件 / 消息队列；拥有服务发布事实，消费者只依赖事件契约，不直连源表
3. **编排**：上游编排服务调用拥有服务接口，禁止编排层「为省一次 hop」直连库

禁止以「内部网、只读账号、共享 SQLite 文件、复制 Model 定义」等理由绕过本条。

##### 数据表迁移出去（路径 B）

迁表时须同时满足：

1. **新 owner 唯一**：目标服务成为该表唯一直连方，并接管 migration / schema
2. **切断旧直连**：源服务移除对该表的 Model、DAO、连接配置与旁路 SQL；产品路径不得残留双写
3. **协作改接口**：原依赖方改为调用新 owner 的 API 或消费其领域事件
4. **文档同步**：设计/意图文档与「表 → owner」对照表更新；未上线阶段（见 `00_project_constraints.md` 第 16 条）可一次性破坏性迁移，无需为旧共享形态保留兼容层

##### 与 DDD / 仓储的关系

- 拥有服务内：表访问仍须落在 **基础设施仓储/适配器**，领域层不直连 ORM（见 `.ai/03_technical_implementation/09_domain_driven_design.md`）。
- 跨上下文：优先 **领域事件或明确应用服务 API**，与「领域边界清晰、禁止跨聚合直连存储」一致。
- 本规则约束的是 **进程间存储边界**；进程内模块拆分不得借「同进程」把本属他服务的表再开第二套直连。

##### 明确例外（须可审计）

以下不视为违规，但须在代码或运维文档中可追溯：

| 例外 | 说明 |
| --- | --- |
| 拥有服务自身的多实例 / 只读副本 | 同一服务的水平扩展或由其管理的只读副本；连接仍属该 owner |
| 迁移与运维工具 | 仅由 owner 团队执行的 `migrate`、备份、经批准的 DBA 只读诊断 |
| 自动化测试隔离 | 测试用内存库、fixture、test double；不得把「测试可直连」带入产品路径 |
| 一次性数据修复脚本 | 经评审、有时限、由 owner 执行；禁止固化为常驻第二写入方 |
| 外部托管 SaaS 数据面 | 第三方官方 API 为唯一入口时，本仓库服务不得再直连其底层库（若可见） |

**非例外**：报表服务、搜索索引、另一业务服务「临时查一下」、管理后台旁路 SQL、共享 `DATABASE_URL`。

### 最佳实践

- 设计阶段先画 **表 → owner 服务** 对照表；发现多服务需要同一表时，优先：**服务转发**、**迁表到正确 owner**、拆表、或由 owner 同步只读投影——而不是共享库。
- 连接串与凭证按服务隔离；CI/配置扫描中避免多服务清单指向同一生产库名（测试库除外且须标注）。
- Review 检查清单：新增 `models`/`ent`/`GORM` 映射或 SQL 时，确认本服务是否为该表 owner；否则改为调用 owner API，或启动迁表使本服务成为唯一 owner。

### 对照表与 CI（落地）

| 产物 | 路径 |
| --- | --- |
| 机器可读对照表 | `db/table_ownership.yaml` |
| 人读摘要 | `docs/architecture/table-to-owner.md` |
| 扫描脚本 | `db/scripts/ci/check_single_service_db_ownership.py`（经 `runAll/scripts/ci/check_ddd_bdd_compliance.py` 调用） |

新增表或变更 owner 时须同步更新 `table_ownership.yaml`；存量跨服务直连须登记 `known_cross_service_access` 并限期整改。
