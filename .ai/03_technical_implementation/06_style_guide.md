## 规则分类

### 风格指南
&gt; 统一代码风格和格式的规范

#### Python代码规范
- 描述：规范Python代码的组织和命名
- 适用场景：所有Python代码开发
- 优先级：低
- 规则：
  - 禁止在一个Python文件中存放多个类
  - 文件命名必须体现文件的内容，使用清晰、描述性的名称
  - 每个Python类应单独存放在一个文件中，文件名应准确反映类的功能或名称

#### Django特有的文件命名要求
- 描述：规范Django项目的文件组织和命名
- 适用场景：所有Django项目开发
- 优先级：低
- 规则：
  - 采用文件命名转为模块命名的方式，以目录作为模块，所有大型文件必须拆分为目录结构
  - 遵循Django框架的标准命名约定，所有包含多个类或函数的文件必须拆分为目录模块：
    - 视图文件：`views.py` → 必须拆分为`views/`目录下的多个模块文件
    - 模型文件：`models.py` → 必须拆分为`models/`目录下的多个模块文件
    - 表单文件：`forms.py` → 必须拆分为`forms/`目录下的多个模块文件
    - 序列化文件：`serializers.py` → 必须拆分为`serializers/`目录下的多个模块文件
    - 认证后端文件：`backends.py` → 必须拆分为`backends/`目录下的多个模块文件
    - 中间件文件：`middleware.py` → 必须拆分为`middleware/`目录下的多个模块文件
    - 信号文件：`signals.py` → 必须拆分为`signals/`目录下的多个模块文件
  - 例外情况：单个类或函数的小型文件可以保留为单个文件，但优先推荐使用目录结构

#### 错误处理与排查
- 描述：规范错误处理和排查的流程
- 适用场景：所有项目错误处理和排查
- 优先级：低
- 规则：
  - 当出现一个错误时，需要查看项目中其他位置是否还存在同样的错误
  - 在修复错误时，使用搜索工具（如grep、IDE搜索功能）检查项目中是否存在相同或类似的错误，确保一次性修复所有同类问题

#### 视觉风格
- 描述：定义项目的视觉风格规范
- 适用场景：所有前端UI开发
- 优先级：低
- 规则：
  - 主色：#7241F2（紫曜律动）
  - 辅助色：#F1F2F6
  - 点缀色：#FF324D
  - 确保主题色→页面→组件→UI控件→组件状态→API端口→后端接口→数据库模型的完整一致性

#### 表名设计规范
- 描述：规范数据库表名的设计和命名
- 适用场景：所有数据库表设计
- 优先级：低
- 规则：
  - 表名格式：采用 `{职能}_{角色}` 的格式设计表名
  - 固定部分前置：职能部分应包含尽可能固定的部分，放在表名前面
  - 命名原则：使用小写字母，单词之间用下划线分隔，避免使用特殊字符和空格
  - 示例：`project_task`（项目任务表）、`user_profile`（用户资料表）

#### 数据库 Migration 字段顺序规范
- 描述：规范后端数据库 migration 文件中字段的声明顺序，确保 ID 字段始终位于第一列
- 适用场景：所有 Django 或类似框架的 migration 文件（如 `migrations/*.py` 中的 `CreateModel`、`AddField` 等操作）
- 优先级：中
- 规则：
  - **ID 字段第一列**：在 `migrations.CreateModel` 的 `fields` 列表中，`id` 字段（或主键字段）必须作为第一个字段声明
  - **继承模型特殊处理**：对于继承自 `AbstractUser`、`AbstractBaseUser` 等基类的模型，自定义的 `id` 字段（如 `SnowflakeIDField`）应放在 `fields` 列表的最前面，然后再列继承的字段（如 `password`、`last_login` 等）
  - **一致性原则**：所有新建或修改的 migration 文件均应遵守此顺序，便于阅读和 diff 比较
  - **编写与审查**：创建 migration 时注意调整字段顺序；对 AI 生成或迁移工具自动生成的 migration，应在提交前检查并调整

#### 数据库 Model 与 Migration 对应规范
- 描述：确保每个 Model 都有对应的 migration 文件，保证数据库 schema 与模型定义同步
- 适用场景：所有 Django 或类似框架的 Model 开发、模型新增或修改
- 优先级：高
- 规则：
  - **一一对应**：每个 Model 类（包括非抽象基类、非代理模型）的创建和字段变更，必须在对应 app 的 `migrations/` 目录下有对应的 migration 文件记录
  - **新增 Model**：新增 Model 后必须执行 `makemigrations` 生成 migration，不得遗漏
  - **修改 Model**：修改 Model 字段（增删改）后必须执行 `makemigrations` 生成 migration，不得直接修改已有 migration 文件内容（除非是明确的数据迁移场景）
  - **合并迁移**：禁止随意删除或合并已应用到生产环境的 migration 文件；新环境应从 `0001_initial` 等初始 migration 开始按顺序执行
  - **提交前检查**：在提交涉及 Model 变更的代码前，应检查 `python manage.py makemigrations --check --dry-run` 无未生成的迁移，确保无遗漏

#### 模型字段 Null 禁止规范
- 描述：模型中的字段除非有明确说明，否则禁止设为 Null（即禁止使用 `null=True`）
- 适用场景：所有 Django 或类似框架的 Model 字段定义
- 优先级：高
- 规则：
  - **默认禁止 Null**：定义 Model 字段时，默认不得使用 `null=True`，应使用非空约束或提供默认值
  - **明确说明例外**：若有业务需求必须允许 NULL（如可选外键、需区分空字符串与 NULL 等），需在字段旁添加注释明确说明原因
  - **字符串字段**：对于 CharField、TextField 等字符串类型，应使用 `blank=True` 配合空字符串 `''` 表示可选，而非 `null=True`
  - **外键可选**：外键字段若允许为空，使用 `null=True, blank=True` 时，需在注释中说明该关系为可选的业务原因

#### 外键禁止与业务层关联规范
- 描述：后端模型中除非明确约定，否则禁止使用 ForeignKey、OneToOneField、ManyToManyField 等外键字段；数据库表之间的关联应在业务层通过 ID 等字段自行维护
- 适用场景：所有 Django 或类似框架的 Model 定义、新增或修改
- 优先级：高
- 规则：
  - **默认禁止外键**：定义 Model 时，不得使用 ForeignKey、OneToOneField、ManyToManyField 等 ORM 级关联字段
  - **业务层维护关联**：表与表之间的逻辑关联（如主从、父子、多对多等）应通过业务层实现：使用普通字段（如 IntegerField、CharField 存储关联 ID），在业务逻辑中显式查询、校验和组装关联数据
  - **明确约定例外**：若经团队或项目明确约定确需使用外键字段（如复杂级联、强一致性要求等），须在 Model 或相关设计文档中注明原因和适用范围
  - **适用框架**：适用于 Django、SQLAlchemy 等 ORM 框架的模型定义

#### 动态外键双字段规范
- 描述：模型中涉及动态外键（即关联目标可能是多种不同模型之一）时，应拆分为两个字段：一个字段标记外键所属的模型，另一个字段存储外键的 ID
- 适用场景：所有涉及多态关联、通用关联或动态外键的 Model 定义、新增或修改
- 优先级：高
- 规则：
  - **双字段结构**：不得使用单一 ForeignKey 或 GenericForeignKey 直接引用；必须采用「模型标记字段 + ID 字段」的双字段设计
  - **模型标记字段**：用于标识外键指向的模型，可存储模型的标识（如 content_type、model_name、app_label + model 等），类型可为 CharField、IntegerField（对应 ContentType.id）等
  - **ID 字段**：用于存储该模型下对应记录的 ID，类型根据主键类型选择（如 BigIntegerField、CharField 等）
  - **业务层解析**：根据模型标记字段和 ID 字段在业务层中解析并获取关联对象，不在 ORM 层使用自动关联
  - **可选辅助字段**：可额外增加 content_type_name 等冗余字段便于查询和展示，但核心结构必须保持双字段

## 规则冲突处理
- 当规则冲突时，遵循以下优先级：
  1. 核心规则 &gt; 最佳实践 &gt; 风格指南
  2. 文件级规则 &gt; 目录级规则 &gt; 全局规则
  3. 新版本规则覆盖旧版本规则
