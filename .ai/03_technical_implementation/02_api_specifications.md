## 规则分类

### 核心规则

#### 异域部署下的 API 与浏览器契约

- 描述：当 **Web 前端访问源** 与 **本 API 公网基 URL** 处于不同域名（跨源）时，接口设计、中间件与错误响应须与 CORS、凭证及回调 URL 策略一致；禁止假设请求均为同源表单提交。
- 适用场景：所有对外 REST/JSON API、文件上传、流式端点及鉴权相关响应头设计。
- 优先级：高
- 规则：细则与检查清单见 [异域前端与 API 域名分离](../01_project_constraints/17_cross_domain_frontend_api.md)；与本文件其他 API 规范同时适用。

#### ID 字段字符串传输（与 API 数字规范交叉）

- 描述：`id` 及 `*_id` 类业务标识在进程内与进程间（含 HTTP JSON）**一律以 string 存在**；仅在写入数据库时转换为 DB 原生类型。
- 适用场景：所有 REST/JSON API、领域事件、跨服务调用；与 Snowflake 主键/外键相关的全部字段。
- 优先级：高
- 规则：完整分层边界、语言要点与禁止事项见 [ID 字段字符串传输规范](./11_id_field_string_transit.md)。本文件下列「数字类型收发」规则仍适用于**非 ID** 数值字段；ID 字段以专文为准且**更优先**。

#### API 端点与序列化器一致性
- 描述：确保API端点与序列化器的一致性和完整性
- 适用场景：所有REST API开发
- 优先级：高
- 规则：
  - 序列化器字段完整性：
    - 前端发送的所有请求字段必须在序列化器中声明
    - 关联字段必须使用正确的RelatedField类型（如PrimaryKeyRelatedField）
    - 字段必须设置正确的required属性
    - 关联字段必须设置正确的queryset
    - 数字类型接收格式：服务端接口接收的所有数字类型（包括整数、浮点数等）必须以字符串形式接收，由服务端自行解析为数字类型
    - 数字类型处理要求：
      - 序列化器中需配置数字字段以字符串形式接收
      - 确保字符串形式的数字在转换为数字类型时不会丢失精度
      - 前后端需约定统一的数字处理方式，避免类型转换错误

  - API 响应字段一致性：
    - 序列化器的fields属性必须包含所有需要返回的字段
    - 避免在视图中手动构建响应数据，优先使用序列化器
    - 对于复杂响应，考虑使用嵌套序列化器
    - 数字类型返回格式：服务端接口返回的所有数字类型（包括整数、浮点数等）必须以字符串形式返回，由客户端自行解析为数字类型
    - 数字类型处理要求：
      - 序列化器中需配置数字字段以字符串形式输出
      - 确保字符串形式的数字在转换回数字类型时不会丢失精度
      - 前后端需约定统一的数字处理方式，避免类型转换错误
    - 布尔类型返回格式：服务端接口返回的所有布尔类型字段必须以 true/false 形式返回，而不是返回字符串
    - 布尔类型处理要求：
      - 序列化器中需确保布尔字段以布尔类型输出
      - 避免将布尔值转换为字符串形式返回
      - 前后端需约定统一的布尔值处理方式，确保类型一致性

  - 关联关系处理：
    - 外键字段必须在序列化器中明确定义
    - 确保关联模型的查询集正确配置
    - 考虑使用select_related或prefetch_related优化查询性能

  - 错误处理与日志：
    - 捕获并处理可能的异常
    - 返回有意义的错误信息
    - 记录关键操作和错误
    - 确保错误响应格式一致
    - 对外错误提示分层：必须同时返回`用户友好错误文案`与`调试细节`
    - 用户友好文案应可直接展示给终端用户（避免堆栈、协议细节、SDK原始报错）
    - 调试细节应结构化暴露在响应中（如 `error_detail`、`error_type`、`request_id`），便于研发快速定位
    - 调试细节必须脱敏，禁止暴露密钥、Token、Cookie、完整账号等敏感信息
    - 对外错误响应建议采用统一结构：`{"status":"error","message":"用户友好文案","error_detail":"调试细节","request_id":"..."}`

  - 测试覆盖：
    - 为每个API端点编写单元测试
    - 测试正常流程和异常情况
    - 测试请求验证和错误处理
    - 定期运行测试以确保API端点正常工作

  - API 幂等性与防重复设计：
    - `/5-nfr` 阶段必须完成「幂等性审视」（元规则 48 / `.ai/01_project_constraints/53_nfr_idempotency.md`）；未通过禁止进入 DDD
    - Kafka / 领域事件**消费实现**须走共享幂等 runner（元规则 49 / `.ai/01_project_constraints/54_event_consumer_idempotency.md`；ADR-0015）
    - 设计API接口时，必须根据业务需要考虑幂等性和防重复请求的设计
    - 对于非幂等操作（如创建、更新等），应实现防重复机制
    - 推荐使用唯一标识符（如UUID）作为幂等键；客户端重试必须回传同一键，禁止每次重试新生成
    - 前端写按钮必须在被接受的点击上生成该键（元规则 52 / `.ai/01_project_constraints/57_frontend_button_anti_replay.md`），经请求头 `Idempotency-Key` 传给本 API
    - 可通过请求头（如 Idempotency-Key / X-Request-ID）或请求体中的唯一标识字段实现
    - 服务端应验证并拒绝重复请求，确保操作的原子性和一致性；幂等键须与业务重复边界同粒度（禁止默认用 tenant/user 级粗字段）
    - 对于金融、支付等关键业务场景，必须实现严格的幂等性保证（NFR ≥ L3）

  - 第三方接口调用规范：
    - 后端代码在请求第三方接口时，禁止直接调用 requests 库
    - 必须使用统一的 HTTP 客户端封装类（如 HTTPClient）进行所有网络请求
    - 封装类应提供统一的错误处理、日志记录和请求/响应处理机制
    - 所有第三方接口调用必须通过封装类进行，确保代码的可维护性和一致性
    - 封装类应位于核心工具模块中，便于全局复用和管理

## 规则冲突处理
- 当规则冲突时，遵循以下优先级：
  1. 核心规则 &gt; 最佳实践 &gt; 风格指南
  2. 文件级规则 &gt; 目录级规则 &gt; 全局规则
  3. 新版本规则覆盖旧版本规则
