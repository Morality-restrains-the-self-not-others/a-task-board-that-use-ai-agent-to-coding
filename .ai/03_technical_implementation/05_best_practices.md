## 规则分类

### 最佳实践
&gt; 提升开发效率和代码可维护性的建议

#### 设计模式
- 描述：规范设计模式的使用
- 适用场景：所有需要使用设计模式的场景
- 优先级：中
- 规则：
  - 遵循 GOF（Gang of Four）23种设计模式进行开发
  - 根据业务场景选择合适的设计模式，优先考虑创建型、结构型和行为型三大类设计模式
  - 确保设计模式的使用符合其原始意图，避免过度设计
  - 对设计模式的使用进行文档化，便于团队成员理解和维护

#### 前端框架
- 描述：规范前端框架的使用
- 适用场景：所有前端开发
- 优先级：中
- 规则：
  - 统一使用 TailwindCSS，通过控制组件的显示与隐藏实现交互，避免动态注入 HTML
  - 采用 Vue 组件化开发模式，拆分组件，避免单个页面包含过多业务逻辑

#### 环境隔离
- 描述：规范项目环境的隔离和管理
- 适用场景：所有项目环境配置和管理
- 优先级：中
- 规则：
  - 项目运行环境、项目单元测试环境和项目自动化测试环境必须放置于不同的 venv（Python虚拟环境）中
  - 禁止将上述环境的运行环境混同，确保各环境的依赖隔离和纯净性
  - 每个环境需单独配置依赖文件，明确指定所需依赖版本
  - 环境切换时需严格遵循指定流程，避免依赖冲突

#### Kafka消息队列事件处理
- 描述：规范Kafka消息队列事件处理的实现；并强制「业务意图出现 → 投递对应业务事件」
- 适用场景：所有涉及Kafka消息队列事件处理的项目；所有服务端业务意图的实现
- 优先级：高（意图→事件投递为强制；消费目录与命名为中）
- 规则：
  - **生产侧（强制）**：业务意图被接受后，必须向消息队列投递对应业务/领域事件（经事件总线端口；开发模式可用内存队列）。禁止有意图无事件（纯查询等例外须在 `docs/intents/` 标注）。细则见 `.ai/08_prompt_management/01_intent_driven_development.md`
  - 事件的处理应该放在以事件名称命名的目录中
  - 一个事件的处理脚本应该只处理一个意图
  - 文件名应该以`序号`_`业务意图`.`是否激活`.py 的方式来命名消费脚本
  - 确保事件处理代码结构清晰，便于扩展和维护，每个脚本只处理一个明确的业务意图
  - **新事件派发顺序**：若 Handler 在处理过程中需要派发新事件（如 `send_event`），应将派发操作放在业务逻辑的**最后**执行。避免在逻辑中间派发导致嵌套消费、执行顺序难以理解；先完成当前 Handler 的主逻辑，再派发衍生事件，使事件流保持线性可追踪

#### 开发模式消息队列选择规则
- 描述：规范开发模式下消息队列的选择，避免 Kafka 消费者热重载问题
- 适用场景：本地使用内存领域事件队列时（通过 `conf/port_config.json` 内 `django.messageQueue.memory: true`，或未配置 `messageQueue` 时旧版顶层 `isDev: true`）
- 优先级：高
- 规则：
  - 当 `django.messageQueue.memory` 为 `true`（或未配置 `messageQueue` 且旧版顶层 `isDev` 为 `true`）时，领域事件队列应采用内存实现，而非 Kafka
  - 内存队列模式下可避免 Kafka 消费者进程无法热重载导致的代码版本不一致问题
  - `django.messageQueue.kafka` 为 `true` 或未启用上述内存模式时，使用 Kafka 消息队列
  - 消息队列的切换应通过依赖注入或配置开关实现，确保业务代码无需感知底层消息队列类型
  - 内存消息队列实现应与 Kafka 保持相同的接口语义，便于无缝切换

#### 动态关联处理
- 描述：规范动态关联关系的实现，遵循风格指南中的「动态外键双字段规范」
- 适用场景：所有涉及动态关联关系的项目
- 优先级：中
- 规则：
  - **双字段结构**：动态关联必须采用模型标记字段（如 content_type_id）与 ID 字段（如 object_id）的双字段设计，不得使用单一 ForeignKey 或 GenericForeignKey
  - **设置动态关联时**：除了设置 object_id 和 content_type_id 外，还应该设置 content_type_name 为对应类的名称，便于查询和展示

#### 邮件发送处理
- 描述：规范邮件发送的实现方式
- 适用场景：所有涉及邮件发送的功能实现
- 优先级：中
- 规则：
  - 项目中碰到需要发送邮件的应该是往消息队列中发送一个发送邮件的事件
  - 在消费事件的时候再去发送邮件
  - 确保邮件发送的异步处理，提高系统响应速度和可靠性

#### SSE发送处理
- 描述：规范SSE (Server-Sent Events) 的发送实现方式
- 适用场景：所有涉及SSE发送的功能实现
- 优先级：中
- 规则：
  - 项目中需要发送SSE的场景，应该通过消息队列的处理函数来发送
  - 具体实现方式：先往消息队列中发送一个SSE事件，然后在消费事件的处理函数中实际发送SSE
  - 确保SSE发送的异步处理，提高系统响应速度和可靠性
  - 避免在直接的业务逻辑中同步发送SSE，减少业务处理的阻塞时间
  - 对于发送到前端的SSE消息，应该对每个消息定义一个专用事件名称，事件名称应该放在data中
  - 事件名称应清晰反映消息的类型和用途，便于前端识别和处理不同类型的消息

#### 邮件模板管理
- 描述：规范邮件模板的创建和使用
- 适用场景：所有涉及邮件发送的功能实现
- 优先级：中
- 规则：
  - 创建新的邮件时，应该先创建一个对应的邮件模板
  - 邮件模板应包含纯文本和HTML两种格式
  - 邮件模板文件应放在 `accounts/templates/email/` 目录下
  - 邮件发送时应使用模板文件生成邮件内容，而不是硬编码邮件内容
  - 模板文件命名应清晰反映邮件的用途（如 verification_code、activation、password_reset 等）

#### Django 函数式编程规范
- 描述：规范Django开发中函数式编程的使用，提高代码可测试性
- 适用场景：所有Django功能开发，特别是新增功能
- 优先级：高
- 规则：
  - 对于新增功能，除非是Django自身的类库（如视图类、模型类等），否则应采用函数式编程的方式实现
  - 函数应作为第一类对象进行传递，而不是采用 import 的方式来传递函数
  - 每个函数应该只执行一个意图，保持功能单一性
  - 函数应保持纯函数特性，输入相同参数应返回相同结果，避免依赖外部状态
  - 函数应职责单一，专注于完成特定任务
  - 函数应易于测试，可通过传入参数和断言返回值进行单元测试
  - 对于每个函数，应该对应的撰写其对应的测试文件，以确保修改的时候，不会破坏原有的功能意图
  - 对于复杂业务逻辑，应拆分为多个小函数，每个函数负责一个具体功能
  - 避免在函数中直接操作全局状态或进行副作用操作，如需进行副作用操作应通过参数注入或回调函数处理
  - 避免在函数中定义新的函数，应将内部函数提取为独立的顶层函数，提高代码可读性和可测试性
  - 函数命名应清晰反映其功能，便于理解和使用
  - 做好函数的命名组织管理，确保相同职能的函数会放在相同的位置
  - 函数组织原则：
    - 按功能模块划分：将相同业务领域的函数放在同一模块或目录中
    - 按功能类型划分：将具有相似功能的函数（如验证函数、处理函数、转换函数等）分组存放
    - 模块命名应反映其包含函数的职能，使用清晰、描述性的名称
    - 对于跨模块共享的函数，应放置在专门的公共函数库中
  - 一个文件仅放一个函数，文件名即函数名
  - 在文件旁边需要放置该函数的单元测试，测试文件名格式为 `{函数名}_test.py`
  - 修改函数后，应该执行对应单元测试以确保函数的原有职能意图没有被破坏

## 规则冲突处理
- 当规则冲突时，遵循以下优先级：
  1. 核心规则 &gt; 最佳实践 &gt; 风格指南
  2. 文件级规则 &gt; 目录级规则 &gt; 全局规则
  3. 新版本规则覆盖旧版本规则
