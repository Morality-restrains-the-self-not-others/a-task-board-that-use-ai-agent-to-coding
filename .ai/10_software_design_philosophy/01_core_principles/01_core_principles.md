## 核心原则

### 1. 复杂性管理
- **核心挑战**：软件设计的核心挑战是管理复杂性
- **复杂性定义**：任何与软件系统结构相关的、使其难以理解和修改的东西
- **复杂性症状**：
  - 变更放大：简单变更需要修改多个地方
  - 认知负荷：开发者需要吸收大量信息才能安全完成任务
  - 未知的未知：不清楚需要修改哪些代码或需要什么信息
- **复杂性根源**：
  - 依赖：代码不能孤立理解或修改
  - 模糊性：重要信息不明显
- **关键洞察**：复杂性是递增的，通过成千上万的小决策积累而成，因此必须采取零容忍的态度

### 2. 战略性编程 vs 战术性编程
- **战术性编程**（反模式）：
  - 目标：尽快让功能工作
  - 心态："只要让它工作"，"我们以后再重构"
  - 结果：复杂性快速积累，技术债务螺旋上升
- **战略性编程**（推荐）：
  - 目标：产生优秀的设计；工作代码是副产品
  - 心态：投资约 10-20% 的开发时间用于设计改进
  - 实践：
    - 寻找机会在每次变更时改进设计
    - 工作代码还不够，设计质量同样重要
    - 软件开发的增量应该是抽象，而不是功能

### 3. 深度模块
- **核心隐喻**：将模块视为矩形
  - 宽度 = 接口复杂性
  - 高度/深度 = 内部隐藏的功能量
- **深度模块**：简单接口，丰富实现（良好设计）
- **浅模块**：复杂接口，功能很少（不良设计）
- **经典例子**：
  - 深度：Unix 文件 I/O — 仅 5 个系统调用（open, read, write, lseek, close）暴露强大的文件系统
  - 浅：Java I/O — 读取文件需要组合 FileInputStream, BufferedInputStream, ObjectInputStream 等
- **实践原则**：
  - 设计接口时，使最常见的用法尽可能简单
  - 简单的接口比简单的实现更重要
  - 罕见用例可以接受更复杂的调用模式，但常见路径不应为此付出代价

### 4. 信息隐藏与信息泄露
- **信息隐藏**：
  - 每个模块应封装设计决策（知识），只暴露简化的接口
  - 隐藏的信息包括：数据结构、算法、低级机制、策略决策
  - 信息隐藏最小化模块间依赖
- **信息泄露**（红旗）：
  - 当相同的设计决策反映在多个模块中时，信息已泄露
  - 时间分解是常见来源：按执行顺序拆分模块（而非按信息隐藏）导致步骤共享过多知识
- **修复泄露**：
  - 将共享知识合并到单个模块中
  - 如果合并不可能，将共享信息统一到单个深度模块后面

### 5. 通用目的 vs 专用模块
- **核心原则**：通用目的模块通常更深
- **原因**：通用接口比专用接口更简单，因为它用更少的方法覆盖更多用例
- **设计新模块时的问题**：满足当前需求的最通用目的接口是什么？
- **判断标准**：
  - 接口应足够通用，无需修改即可支持多种用例
  - 但实现可以只做当前需要的事情（不要过度构建）
  - 通用目的和专用代码应清晰分离

### 6. 不同层级，不同抽象
- **原则**：软件系统有多个层级；每个层级应提供与其相邻层级不同的抽象
- **如果两个层级有相似的抽象，分层是错误的**
- **直通方法**（红旗）：
  - 几乎不做任何事情，只是将参数转发给具有相似签名的另一个方法
  - 这表明层级不提供不同的抽象 — 责任划分有缺陷
- **直通变量**（红旗）：
  - 从顶层到底层穿过不使用它的层级的变量
  - 解决方案：上下文对象、依赖注入或重新思考模块边界

### 7. 将复杂性向下拉
- **核心原则**：当复杂性不可避免时，模块应在内部吸收它，而不是推给调用者
- **原因**：大多数模块的用户比开发者多 — 开发者受苦总比每个用户都受苦好
- **反模式**：
  - 将艰难决策变成配置参数并推给系统管理员
  - 为不确定条件抛出异常并让调用者处理
  - 这些在短期内节省精力，但会放大系统范围的复杂性

### 8. 通过重新定义语义消除错误
- **核心洞察**：
  - 异常处理是复杂性的最大来源之一
  - 减少必须处理的异常数量是减少复杂性的最佳技术之一
- **策略**：
  1. **重新定义语义**，使错误条件无法出现
     - 示例：`unset(key)` 即使键不存在也成功 — 它只是保证"调用后，键不存在"
     - 示例：`substring(start, end)` 自动裁剪越界参数而不是抛出异常
  2. **异常屏蔽**：在低级别检测并处理异常，使其永远不会到达调用者
  3. **异常聚合**：在一个集中的地方处理多种异常类型，而不是在每个调用点分散处理
- **重要区别**：这不是关于忽略错误 — 而是关于**设计更好的语义，使错误条件根本不是错误**
- 真正需要报告的错误（例如，丢失的网络数据包）仍必须正确处理

### 9. 设计两次
- 对于任何重要的设计决策，在选择之前构思**至少两种不同的方法**
- 即使第一个想法看起来很棒，也要强迫自己思考替代方案
- 比较维度：接口简单性、通用性、性能、实现难度
- 这种习惯显著提高设计质量

### 10. 注释哲学
- **为什么写注释**：
  1. 注释捕获代码无法表达的设计决策和意图
  2. 注释是抽象的一部分 — 良好的接口文档意味着用户不必阅读实现
  3. 早期写注释在投入代码之前暴露设计问题
  4. 良好的注释显著减少认知负荷
- **注释应描述什么**：
  - **非明显信息**：原因、约束、边界条件、副作用 — 代码中看不到的东西
  - 注释不应重复代码已经说的内容
- **注释层级**：
  - **接口注释**：描述做什么和为什么 — 无实现细节
  - **实现注释**：解释如何以及为什么采用这种方法 — 代码为什么这样写
  - **跨模块注释**：记录跨越模块边界的设计决策和依赖
- **注释优先方法**：
  - 在编写实现之前编写接口注释 — 将注释用作设计工具
  - 如果你不能写清晰的注释，设计本身可能有问题

### 11. 命名艺术
- **好名字的标准**：
  - **精确**：向读者传达含义，无歧义
  - **一致**：相同的名字在整个代码库中始终表示相同的事物
  - **信息丰富**：好名字本身就是轻量级文档
- **命名红旗**：
  - **模糊名字**：太通用（例如，`data`、`result`、`tmp`、`info`）— 不携带有用信息
  - **难以命名**：如果你难以找到精确、直观的名字，设计本身可能有缺陷

### 12. 一致性
- 在整个系统中**以相同的方式处理相同的事物**
- 一致性涵盖：命名、编码风格、接口模式、设计模式、不变量
- 一致性显著减少认知负荷 — 一旦开发者学习了一种模式，它适用于所有地方
- 不要为了"更好"而破坏一致性，除非改进足够显著并且旧方式可以完全替换

### 13. 代码应该明显
- **目标**：读者应该能够快速理解代码的行为和意图，无需大量脑力劳动
- **明显性是良好设计的最终测试**
- **明显代码的技术**：
  - 良好的命名和一致性
  - 明智地使用空白和格式来揭示结构
  - 解释非明显内容的注释
  - 避免事件驱动代码中的隐式控制流（除非必要）
- **非明显代码**（红旗）：
  - 如果读者不能轻松理解代码的行为或含义，它就不够明显

### 14. 红旗快速参考

| 信号 | 含义 |
|------|------|
| **浅模块** | 接口几乎与其实现一样复杂 |
| **信息泄露** | 相同的设计决策反映在多个模块中 |
| **时间分解** | 模块按执行顺序拆分，而非按信息隐藏 |
| **过度暴露** | 通用 API 迫使调用者了解很少使用的功能 |
| **直通方法** | 方法只是将参数转发给具有相似签名的另一个方法 |
| **重复** | 非平凡代码在多个位置重复 |
| **特殊-通用混合** | 通用目的和专用代码未清晰分离 |
| **联合方法** | 理解一个方法需要理解另一个方法 |
| **注释重复代码** | 注释只是代码的英文翻译 |
| **实现污染接口** | 接口文档暴露用户不需要的实现细节 |
| **模糊名字** | 名字太通用，无法传达有用信息 |
| **难以选择名字** | 找不到精确、直观的名字 — 设计可能有缺陷 |
| **难以描述** | 文档必须很长才能完整 — 模块可能太复杂 |
| **非明显代码** | 代码的行为或含义不容易理解 |

### 15. 设计原则摘要

1. 复杂性是递增的 — 关注细节
2. 工作代码还不够
3. 持续进行小的投资来改进系统设计
4. 模块应该深
5. 接口应该使最常见的用法尽可能简单
6. 简单的接口比简单的实现更重要
7. 通用目的模块更深
8. 分离通用目的和专用代码
9. 不同层级应该有不同的抽象
10. 将复杂性向下拉
11. 消除错误（和特殊情况）
12. 设计两次
13. 注释应该描述代码中不明显的内容
14. 软件应该为易于阅读而设计，而不是为易于编写
15. 软件开发的增量应该是抽象，而不是功能
